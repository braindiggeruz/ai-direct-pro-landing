# Scrapling → Lead Radar: оценка и roadmap интеграции

Дата: 2026-08-31. Статус: исследование и предложение, не реализованный релиз.

## 1. Решение

**Scrapling подходит как движок получения публичных страниц для отдельного локального сборщика. Его стоит интегрировать, завершив уже существующий пилот, а не переписывая Lead Radar.**

Первый продуктовый результат: для уже найденных компаний получать дополнительные опубликованные телефоны, Telegram-ссылки и общие email с официальных сайтов, сохранять доказательства и продолжать работу при недоступности отдельных источников.

Это не готовая база компаний и не инструмент, автоматически превращающий телефон в доступного получателя Telegram. Поиск компаний, сопоставление бизнеса, разрешение Telegram-контакта и допуск к рассылке остаются отдельными задачами.

Разделять всегда: найденная компания → опубликованный контакт → доказанная принадлежность → подтверждённый Telegram endpoint → допустимый получатель → подготовленная кампания. Сам сбор ничего не отправляет и не создаёт основание для рассылки.

## 4. Что полезно взять, а что не переносить автоматически

| Возможность | Польза в Lead Radar | Ограничение |
| --- | --- | --- |
| HTTP Fetcher | Быстрый первый проход сайтов и страниц контактов | Не каждый сайт отдаёт контакты без JavaScript |
| Browser fetcher | Чтение контактов, появляющихся после исполнения JavaScript | Дороже по памяти и времени; нужен небольшой отдельный пул |
| CSS/XPath и adaptive matching | Поддержка адаптеров каталогов при изменении разметки | Сходство элемента не доказывает принадлежность телефона компании |
| Async requests, приоритеты | Обработка независимых сайтов параллельно | URL-дедупликация не равна объединению компаний |
| Streaming результатов | Показывать и сохранять находки по мере поступления | Нужны надёжное подтверждение записи и повторная доставка |
| Checkpoint | Возобновлять очередь URL после штатной паузы | Не сохраняет всю бизнес-операцию, cooldown и подтверждение сохранения находок |
| MCP | Помощь инженеру при исследовании источника | Не заменяет production API, очередь или ограничения доступа |

В базовом потоке не нужны LLM, embeddings или платные API. Adaptive matching работает через сравнение структуры; включать его только в проверенных адаптерах, отдельно от правил доверия. [Adaptive scraping](https://scrapling.readthedocs.io/en/latest/parsing/adaptive.html), [интерфейсы fetchers](https://github.com/D4Vinci/Scrapling/tree/458e2a2ac909b3235747ebcdb312b93a1080a10a/scrapling/fetchers).

### Критические особенности версии 0.4.15

1. **Безопасную частоту запросов необходимо настроить самим.** У Spider по умолчанию `robots_txt_obey=False`, AutoThrottle выключен, per-domain concurrency не ограничена и download delay равен нулю. [Настройки Spider](https://github.com/D4Vinci/Scrapling/blob/458e2a2ac909b3235747ebcdb312b93a1080a10a/scrapling/spiders/spider.py#L73).
2. **Retry-After может быть сокращён.** Включённый AutoThrottle ограничивает даже серверный Retry-After значением max_delay; стандартное значение — 60 секунд. В тесте явно зафиксирован случай 3600 → 60. Нужен внешний сохраняемый срок следующей попытки, без сокращения серверной паузы. [Throttle](https://github.com/D4Vinci/Scrapling/blob/458e2a2ac909b3235747ebcdb312b93a1080a10a/scrapling/spiders/throttle.py#L89), [тест](https://github.com/D4Vinci/Scrapling/blob/458e2a2ac909b3235747ebcdb312b93a1080a10a/tests/spiders/test_throttle.py#L159).
3. **Robots fail-open.** Ошибки загрузки и non-200 превращаются в пустые разрешающие правила. Наша политика должна различать отсутствие файла и временную недоступность/запрет; последние не должны молча разрешать обход. Проверять фактический User-Agent, полный origin и ограничения частоты. [Robots manager](https://github.com/D4Vinci/Scrapling/blob/458e2a2ac909b3235747ebcdb312b93a1080a10a/scrapling/spiders/robotstxt.py#L28).
4. **Checkpoint не является durable job queue.** Сохраняются запросы и seen set; используется pickle. Не принимать чужие checkpoint-файлы, изолировать локальный каталог. Найденные результаты, подтверждения доставки и cooldown хранить отдельно. [Checkpoint](https://github.com/D4Vinci/Scrapling/blob/458e2a2ac909b3235747ebcdb312b93a1080a10a/scrapling/spiders/checkpoint.py).
5. **Development cache не подходит для доказательства свежести.** Он хранит полное содержимое/заголовки/cookies без TTL; cached response может миновать обычную классификацию blocked status. В production оставить development mode выключенным. [Cache](https://github.com/D4Vinci/Scrapling/blob/458e2a2ac909b3235747ebcdb312b93a1080a10a/scrapling/spiders/cache.py), [engine](https://github.com/D4Vinci/Scrapling/blob/458e2a2ac909b3235747ebcdb312b93a1080a10a/scrapling/spiders/engine.py#L199).
6. **Есть HTTP safe redirects, но этого недостаточно для нашего сервиса.** Fetcher по умолчанию передаёт `follow_redirects="safe"`. Это не проверенное нами end-to-end доказательство защиты исходного URL, DNS-перепривязки и browser subresources. Нельзя публиковать benchmark как произвольный URL fetch endpoint. [HTTP engine](https://github.com/D4Vinci/Scrapling/blob/458e2a2ac909b3235747ebcdb312b93a1080a10a/scrapling/engines/static.py#L673).

## 5. Предлагаемая архитектура

```text
Lead Radar: ниша / город / сохранённые компании
  → существующая серверная очередь + новый адаптер crawler jobs
  → отдельный Windows-сборщик Scrapling, исходящие соединения
  → ограниченные страницы / факты / источник / время / digest
  → канонические TypeScript-правила Lead Radar
  → подтверждение принадлежности компании
  → отдельная очередь проверки Telegram через существующий Bridge
  → проверка основания, запретов, истории и лимитов
  → предпросмотр кампании и одно финальное подтверждение отправки
```

Cloudflare оставляем владельцем заданий, состояния и допуска. Локальный процесс выполняет тяжёлую загрузку и JavaScript. Python Workers существуют, но поддерживают определённые WebAssembly-совместимые пакеты; из этого не следует совместимость полного CPython/curl/browser стека Scrapling с нашим Pages handler. Выбор локального процесса — архитектурное решение на основе стека и существующего Windows-пилота, не утверждение «Cloudflare не поддерживает Python». [Официальная документация](https://developers.cloudflare.com/workers/languages/python/packages/).

Сборщик отделить от Telegram Bridge: другой процесс, окружение, каталог данных, credential и права ОС. Отдельный venv сам по себе не защищает файлы Bridge от процесса того же пользователя: нужны отдельная учётная запись/ACL либо эквивалентная sandbox-изоляция. Не использовать owner JWT, Bridge device key, Telegram session, пользовательский Chrome-профиль или Cloudflare admin token.

Существующие lease-проверки сервера не означают наличия Python API. Claim/heartbeat/result receipt для сборщика ещё требуется спроектировать. Нельзя просто подключить Python к `/v1/bridge/*`.

### Новый контракт сборщика — предложение, не существующее API

Задание: version, jobId, orgId, searchId, companyId, identityDigest, leaseGeneration, deadline, allowlisted source/URLs, page/depth/byte/time budgets.

Результат: jobId + generation + idempotency key; requested/final URL; HTTP status; fetchedAt; original observedAt для кеша; content hash; collector/extractor versions; ограниченный артефакт либо доказательный контекст; partial/completed/deferred/error и следующий допустимый срок.

Сервер отклоняет новые результаты с истёкшей lease, чужим tenant, изменившейся компанией, отменённым заданием, запрещённым источником и повторную несовместимую запись. При потере ACK сначала сверять сохранённый receipt: уже принятый результат подтверждается без нового применения, даже если его lease впоследствии истекла. Результат сборщика никогда не содержит доверенного `ready_to_send` или нового основания для отправки.

Парсер TypeScript остаётся единым. Сначала измерить его CPU/размер входа на одной странице в фоне, отдельно от HTTP-запроса владельца. Если не укладывается в бюджет Workers, вынести вычисление того же модуля в изолированный локальный Node-процесс, не писать второй Python-классификатор. Серверный admission и проверка целостности/области доказательств остаются обязательными: content hash не доказывает принадлежность контакта; проверяется связка задания, компании, источника и доказательного контекста. Не пересылать десятки полных DOM в один запрос админки.

## 6. Roadmap по приоритетам

### Этап 0 — закрепить baseline и критерии результата

- Переиспользовать pilot, lockfiles и fixtures; не смешивать зависимости со службой Bridge.
- Сохранить исходные метрики текущего парсера на той же выборке; исторические цифры не считать свежим baseline.
- Подготовить размеченные примеры RU/UZ: один бизнес, филиалы, соседние карточки, чужой разработчик в footer, бот/канал, общий телефон, JS-контакты, отсутствие контакта, 429/503/challenge.
- Метрики: найденные компании; пригодные страницы; корректные уникальные контакты; доказанная принадлежность; Telegram подтверждён; допущен. Для каждой — собственный знаменатель.

Готово: воспроизводимый локальный набор и сравнительный отчёт; ни один показатель не выдаётся за готовую аудиторию без последующих проверок.

### Этап 1 / P0 — надёжная и изолированная доставка заданий

- Outbound polling: claim → heartbeat → result → acknowledgement. Без публичного порта на компьютере.
- Перенять паттерны lease/fencing/idempotency, не полномочия Telegram Bridge.
- SQLite outbox локально: записать результат транзакционно, затем доставлять до подтверждения сервера. Применение на сервере идемпотентно; сеть не даёт гарантии exactly-once сама по себе.
- Ограниченный TTL/объём артефактов, отдельные ACL, скрытая фоновая служба с restart policy. Не сохранять cookies/auth headers и полные персональные страницы в обычных логах.
- Истёкшая heartbeat обозначает «сборщик недоступен», а не «контактов нет». Повторное получение задания не обнуляет доказательства.
- Безопасность URL до первого произвольного сайта: только разрешённые HTTP(S), запрет credentials и локальных/служебных адресов, проверки каждого redirect, transport-level DNS/IP enforcement и browser egress/subresources. Ограничение входящих байтов в процессе чтения, распакованного размера, времени и глубины DOM.

Готово: сценарии обрыва/рестарта/дубликата/старой lease проходят; локальная сеть и vault Bridge недоступны сборщику. Пока egress isolation не доказана, только собственные fixtures и узкая ручная allowlist, без arbitrary URL режима.

### Этап 2 / P1 — первый полезный релиз: официальные сайты

- Брать уже сохранённые компании с известным сайтом; не менять одновременно весь поиск компаний.
- HTTP-first: главная и до четырёх релевантных same-origin страниц, приоритет «Контакты», contacts, kontakt, aloqa. Не обходить блог/магазин целиком ради телефона.
- Переиспользовать TS-извлечение tel, Telegram-ссылок, общих email, JSON-LD и контекста компании.
- Фиксировать URL/время/контекст для каждого факта. Конфликтующий номер или филиал не исправлять догадкой.
- Дедупликация по нормализованному контакту с учётом компании/филиала/tenant; одинаковый номер у разных бизнесов — неоднозначность, не автоматическое слияние.
- Сохранять найденное по мере поступления, не ждать конца всей аудитории.

Готово: карточка показывает новые проверяемые факты и источники; повторный запуск не создаёт дубли. «Не найдено на просмотренных страницах» отделено от «страницу не удалось загрузить».

### Этап 3 / P1 — паузы источников и выборочный JavaScript

- Единственный владелец повторов — durable scheduler Lead Radar. Внутренние повторы SDK либо выключены, либо входят в тот же ограниченный бюджет.
- Сохранять `next_retry_at` по источнику/домену с учётом полного Retry-After; срок не теряется после перезапуска. Учитывать shared egress и суммарные запросы всех задач.
- Источник A на паузе не занимает поток ожиданием и не блокирует B/C; fair host-aware scheduling. Robots-fetch также входит в лимит.
- 429/403/CAPTCHA не отправлять в браузер как автоматическую попытку обойти запрет. JS fallback только когда страница разрешена, но нужный контент действительно требует рендеринга.
- Стартовые параметры для измерений, не обещанная производительность: до трёх HTTP-задач, одна на домен, один browser context; повышение только по ресурсам и правилам источника.
- Серверные cooldown, результаты и outbox первичны; встроенный checkpoint — вспомогательный. Development cache выключен.

Готово: 429 + Retry-After 3600 не вызывает повтор до срока даже после рестарта; независимые сайты завершаются; частичный результат доступен пользователю. Проверить остановку, повреждённый checkpoint и переполнение бюджета.

### Этап 4 / P2 — больше компаний по нишам, а не только больше страниц

- После устойчивого enrichment добавить адаптеры разрешённых публичных отраслевых каталогов; OSM оставить одним из источников, не единственной точкой отказа.
- Ниша/город/язык превращаются в ограниченный план источников. Синонимы RU/UZ и категории фиксировать явно; фильтровать географию и реальные виды деятельности.
- Для компании без сайта сначала искать доказуемую карточку/официальный домен. Имя/slug сами по себе недостаточны для уверенного совпадения.
- Sitemap применять после установления домена и только для выбора полезных страниц; он не является поисковой системой компаний.
- На каждый адаптер: allowlist, политика источника, fixtures, ограничения запросов, ownership criteria, причины отказа и fallback. Никакого сбора участников закрытых чатов или угадывания скрытых контактов.

Готово: каждый адаптер даёт измеренный дополнительный объём корректных уникальных контактов; можно выключить один источник без остановки остальных. Если у компании нет опубликованного контакта, не выдумывать его.

### Этап 5 / P1 — понятный интерфейс и отдельная подготовка кампании

- Сбор/обогащение запускается отдельным серверным заданием, а не долгой цепочкой внутри кнопки «Подготовить рассылку».
- Показывать: обработано / найдено / ждёт источник / ждёт сборщик / неоднозначно / не найдено / исключено. Для паузы — причина и срок; для работы — heartbeat и последняя завершённая компания.
- Вкладку можно закрыть: серверное состояние и локальная очередь сохраняются; при открытии интерфейс сверяется с сервером.
- Давать «Повторить отложенные» без повторной обработки свежих завершённых компаний. Не обещать автоматическое продолжение, если компьютер выключен.
- Уже достаточное свежее доказательство не должно бесконечно ждать необязательного каталога. При необходимости обязательного доказательства статус остаётся отложенным, не превращается в допуск.
- Подготовка кампании использует сохранённые факты, затем отдельные Telegram/basis/history/limit проверки. Одно финальное подтверждение фактической отправки сохраняется; убрать дублирующие подтверждения технических операций.

Готово: больше нет бесконечного «Подготавливаем…» без причины; один проблемный контакт не мешает сформировать проверяемую готовую подгруппу. Ноль готовых получателей означает конкретный список причин, а не молча неактивную кнопку.

Этап 5 можно разрабатывать параллельно с 2–3 после фиксации контракта этапа 1. Контрольная Telegram-проверка — отдельная работа: Scrapling не должен задерживать проверку уже пригодного собственного/согласившегося тестового контакта.

### Этап 6 — shadow pilot, включение и откат

- Сначала собственные fixtures, затем разрешённая фиксированная выборка 15 сайтов, после успешной приёмки расширение до 50–100 компаний по нескольким нишам. Числа — план выборки, не выполненный сбор.
- В shadow режиме сравнить старый и новый путь без изменения допуска/отправки. Не удваивать внешние запросы бесконтрольно: переиспользовать записанные страницы, общий cooldown и лимиты.
- Проверить build/typecheck/релевантные TS и Python тесты, dependency scan закреплённого окружения, CPU/RAM/трафик, очередь и браузерные сценарии.
- Перед production activation: сверить текущую ветку/live, сохранить существующие SEO/admin изменения и rollback manifest; новая интеграция не должна откатить чужие релизы.
- Отдельные выключатели для HTTP provider, JS, каждого каталога и всего collector. Безопасный fallback — старый путь или явное ожидание, не обход запрета источника.
- Откат останавливает выдачу новых заданий, корректно завершает/отменяет leases и сохраняет принятые факты/outbox для контролируемой сверки. Не удалять аудитории и доказательства.

Готово: измерения показывают добавленную пользу без потерь/ошибочного допуска. Реальный тест отправки — только отдельный явно разрешённый микропилот на собственный или согласившийся контакт с известным текстом, без массового запуска из crawler.

## 7. Обязательные приёмочные проверки

| Проверка | Ожидаемый результат |
| --- | --- |
| 429 с паузой на час; рестарт в середине | Повтор не раньше срока; другой домен продолжает работу |
| Десять заданий одного paused host перед здоровым host | Здоровый host не ждёт освобождения всех «спящих» запросов |
| Robots 503/timeout/403 и отдельный допустимый случай отсутствия файла | Различимые решения политики, не универсальное allow-all |
| Убийство процесса после извлечения и до ACK | Результат восстанавливается; на сервере одна запись |
| Дубликат batch / старая lease / смена company identity / DNC | Повтор безопасен либо отклонён; устаревшая запись не принята |
| Главная без контакта, контакт на JS-странице | Выборочный render; доказательство включает правильный источник |
| Чужой телефон в footer или соседней карточке | Не становится корпоративным контактом искомой компании |
| Telegram bot/channel/group или неоднозначная ссылка | Не превращается в подтверждённого получателя |
| Redirect/DNS/subresource в private, loopback, metadata, IPv6 local | Соединение блокируется до доступа к цели |
| Огромный/сжатый ответ, бесконечные ссылки, долгий JS | Срабатывают byte/time/page/memory budgets; heartbeat жив |
| Cached 429, старый HTML, challenge с HTTP 200 | Нет ложного свежего доказательства контакта |
| Закрытие вкладки / сон компьютера / потеря сети | Понятный статус и продолжение без ручного обнуления |
| Повторная подготовка кампании | Не делает повторный полный crawl и не отправляет сообщений |

## 8. Метрики и цена

Цель — не максимальное число телефонов, а **стоимость и время получения корректного уникального корпоративного контакта**.

Измерять отдельно: время первого сохранённого результата; P50/P95 HTTP и JS; длительность партии с отдельно выделенным внешним ожиданием; пригодные страницы/попытки; контактная точность на ручной разметке; incremental yield; дубли; ошибочная принадлежность; доля JS; число deferred по причинам; RAM/CPU/байты/диск; последующую Telegram-достижимость. Telegram-результат не выдавать за качество загрузчика или наоборот.

Предлагаемый quality gate: все negative/ownership/security fixtures пройдены, потерь результатов и повторных применений при fault tests нет; не менее 95% правильной привязки контактов на размеченном пилоте с явным размером выборки. Это целевой критерий, не полученный результат и не гарантия будущего качества. Неоднозначные случаи — review; критичная ложная принадлежность блокирует включение соответствующего адаптера. Полноту считать лишь на выборке с известными контактами.

Целевое ограничение бюджета: **ноль новых платных API, прокси, LLM и CAPTCHA-сервисов**. Использовать существующий ПК, закреплённые open-source зависимости и текущую инфраструктуру с жёсткими квотами. Это не означает нулевое электричество/интернет/обслуживание или безлимитные облачные ресурсы. При исчерпании разрешённого бюджета — понятная пауза, не незаметный платный fallback. Пока ПК спит, локального сбора нет; для круглосуточности нужен постоянно включённый узел.

## 9. С чего начинать реализацию

Первый законченный vertical slice: **одно серверное задание → изолированный HTTP Fetcher → официальная страница контактов → общий TS extractor → сохранённый факт со ссылкой → видимый результат в карточке → безопасный повтор после обрыва**.

После этого — обработка пауз и JS, затем дополнительные каталоги. Не начинать с stealth/proxy/MCP-платформы или переписывания всей системы. Нельзя обещать «завтра готовая массовая рассылка» только на основании выбора crawler: доступность Telegram и условия отправки проверяются отдельно.

Применённый навык Cloudflare повлиял на разделение локального тяжёлого сборщика и серверного control plane; никаких изменений инфраструктуры в ходе исследования не выполнялось.
