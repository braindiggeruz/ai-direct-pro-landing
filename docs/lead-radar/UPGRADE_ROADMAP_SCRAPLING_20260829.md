# Lead Radar: обновление сбора сайтов и Telegram-контактов

Дата: 2026-08-29. Статус: согласуемый план реализации, НЕ отчёт о внедрении.

Основание: полностью прочитанное исследование «Лучшие бесплатные парсеры для Lead Radar.docx» (93 непустых абзаца), первичные репозитории и ранее выполненный аудит нашей системы. В этом ходе ничего не установлено, production не менялся, новые платные запросы, Telegram-проверки и сообщения не запускались.

## 1. Решение

Основной кандидат для нового локального сборщика — **Scrapling**. Контрольный кандидат и резерв при провале испытаний — **Crawl4AI**. Это решение о том, что проверять и интегрировать, а не утверждение, что Scrapling уже показал лучший результат на наших компаниях.

Сохраняем существующие Lead Radar, Cloudflare Worker/D1, глобальный каталог получателей, защиту кампаний и Telegram Bridge. Добавляем заменяемый адаптер загрузки сайтов. Принадлежность контакта компании, проверка Telegram и разрешение на отправку остаются отдельными серверными решениями.

Для нового маршрута предлагаем режим `free_only`: без обязательного платного API, LLM, прокси или решения CAPTCHA. Уже подключённый Firecrawl не удаляем и не отключаем этим документом. После реализации он может оставаться отдельно разрешаемым резервом с явными лимитами. Отказ бесплатного сборщика не должен незаметно переводить запрос на платный сервис.

Бесплатная лицензия не отменяет расход ресурсов компьютера, интернета и действующей инфраструктуры. При выключенном компьютере локальный сбор ожидает его возвращения. Круглосуточный сервер — отдельное решение, а не обещанная бесплатная услуга.

## 2. Что принимаем и что исправляем в исследовании

| Вывод исследования | Оценка и решение |
| --- | --- |
| Scrapling подходит для локального сбора | Обоснованный кандидат: открытый код, HTTP и браузерный режим. Проверить на нашем Windows и одинаковом наборе сайтов с Crawl4AI. |
| Выбор уже подтверждён тестами | Нет. В документе прямо указано «не проверено запуском». Нет измеренного результата, проекта теста или журнала выполнения. |
| Достаточно `pip install scrapling` | Нет для полного обхода: базовый пакет содержит парсер; загрузчики и браузеры устанавливаются отдельно. Пакетирование — часть пилота. |
| Возобновление обхода решает сбои | Документация описывает checkpoint при штатной остановке. Перезагрузка ПК, аварийное завершение и потеря ответа требуют нашей очереди, квитанций и тестов. |
| Название рядом с телефоном достаточно для привязки | Нет. У нас воспроизведено ложное совпадение по общему слову «Стоматология». Нужны независимые признаки компании и обработка противоречий. |

| Каждый сайт обязан дать контакт; половина телефонов обязана подтвердиться в Telegram | Непригодные критерии. На сайте может не быть публичного контакта; Telegram может не раскрыть результат из-за настроек приватности. |
| Стоимость и скорость уже известны | Нет. Расчёты условные, а часть временной арифметики не согласована. Замеряем время, память, трафик и внешние вызовы на реальном пилоте. |
| Краулер найдёт компании без исходных URL | Сам по себе нет. Поиск официального сайта и извлечение контактов с известного сайта — разные задачи. |

## 3. От какой фактической ситуации отталкиваемся

Это базовая точка из [аудита 29 августа](CONTACT_ACQUISITION_AUDIT_20260829.md), а не свежая проверка production в этом ходе. Срез БД сделан 28 августа в 23:09 UTC, уже 29 августа по местному времени.

- 940 записей компаний в запусках, но 267 различных canonical keys: строки поиска нельзя считать уникальными получателями.
- В последнем проверенном запуске — 127 записей компаний; у 124 исходов поиска источников стояло ограничение бюджета/аренды, у трёх — недостаточная идентификация. Это не 124 доказательства отсутствия контакта.
- За UTC-сутки было зарезервировано 200 внутренних кредитов Firecrawl. Последнему поиску достались 14. Резервирование не равно окончательному списанию провайдером; неопределённые результаты нельзя самовольно возвращать в бюджет или повторять.
- В проверенном срезе — один успешно распознанный корпоративный Telegram peer, ноль записей основания для отправки и ноль кампаний. Это не доказывает текущую готовность Bridge или возможность рассылки сегодня.
- Синтетически подтверждены потери телефонов в `contactPoint.telephone`, структурированных данных и обычном тексте; предпочтение пустого raw HTML перед полезным rendered HTML; пропуск третьего результата поиска; ложная привязка по общему названию; блокировка возобновления закешированным бюджетным отказом.

Новый HTTP/браузерный движок сам не исправляет эти ошибки. Исправление экстрактора и состояний очереди — обязательная часть обновления.

## 4. Целевая архитектура

```text
Ниша + город / существующие компании / предоставленные URL
    → поиск публичных источников и кандидатов официального сайта
    → серверная очередь обхода
    → отдельный локальный Crawler: HTTP → браузер при необходимости
    → общий экстрактор + доказательства со страниц
    → серверная проверка принадлежности и устранение дублей
    → фоновая проверка Telegram через существующий Bridge
    → единый каталог: кандидаты / проверены / доступны для отправки
    → серверный предпросмотр кампании → явный запуск пользователем
```

Worker/D1 остаётся координатором. Локальный Crawler получает задания исходящим авторизованным запросом к Worker; он не предполагается прямым локальным потребителем Cloudflare Queues. Для него нужны отдельные ограниченные права, версионированные задания, lease, heartbeat, идемпотентные результаты и серверная проверка схемы.

Новый компонент предлагается разместить в `tools/lead-radar-crawler/`. Это отдельное окружение и процесс, без импорта Telegram-сессии, API hash и хранилища Bridge. Одного venv недостаточно для изоляции: при упаковке предусмотреть ограниченного пользователя/ACL или эквивалентную песочницу, запрет чтения vault и сетевой доступ только в разрешённых направлениях. Локальные браузерные задания не получают произвольные скрипты или команды из веб-страниц.

Административная вкладка отображает состояние, но не должна быть двигателем очереди. Закрытие страницы не отменяет сбор или проверки. Неизвестный исход операции хранится как неизвестный, а не превращается в успех или повод для бесконтрольного повтора.

### Данные и независимые состояния

Вместо пары `belongs_status=true` / `telegram_verified=true` вводим или расширяем:

- `company` / филиал; `contact_endpoint` (телефон, username или business chat link); связь контакта с компанией; вхождения в поисковые запуски.
- Источник, фактический URL после переходов, фрагмент доказательства, время загрузки, вид HTML и версия экстрактора. Хранение фрагментов ограничено сроком и объёмом; секретов и полного произвольного содержимого в логах нет.
- Принадлежность: `unconfirmed / confirmed / conflict / rejected`, с причинами и версиями правил.
- Telegram: `not_checked / queued / checking / resolved_user / unsuitable_type / privacy_or_missing / retry_at / stale`.
- Основание отправки: отдельная действующая серверная запись с областью применения, сроком и возможностью отзыва.
- Готовность: вычисление сервером на момент проверки/отправки, а не редактируемый флаг, присланный краулером.

Телефон и username могут существовать независимо. Находка мобильного номера не означает Telegram; успешное разрешение username не доказывает его принадлежность компании. `privacy_or_missing` не следует переименовывать в категоричное «Telegram нет».

## 5. Порядок реализации и backlog

Разбиение использует подход agile-product-owner: небольшие пользовательские истории, явные зависимости и проверяемые критерии. Оценки SP предварительные, относительные, не дни. Скорость команды не измерена, поэтому календарное обещание до пилота не даём. Каждый этап закрывается демонстрацией результата.

### Этап 1 — перестать терять уже найденные данные (Critical)

В первый корректирующий релиз также входит независимая серверная часть LR-06: убрать ложное завершение из-за бюджета и обеспечить возобновление временно ограниченных задач. Эту уже подтверждённую ошибку не нужно оставлять до установки нового краулера.

**LR-01, 5 SP.** Как оператор, хочу видеть все публичные контакты, действительно присутствующие в загруженных материалах компании. Зависимостей нет.

Работы: единый provider-neutral экстрактор для имеющегося источника и нового адаптера; `tel:`, видимый текст, JSON-LD включая массивы, `@graph` и `contactPoint.telephone`; Telegram URL/username/business links. Raw и rendered представления обрабатываются раздельно, затем кандидаты объединяются с происхождением. Footer контактов компании сохраняется; контакты разработчиков и виджетов не приписываются компании.

Приёмка:

1. Все соответствующие воспроизведения из аудита переведены из фиксации неправильного поведения в регрессии правильного поведения и проходят.
2. Контакт, присутствующий только в rendered HTML или JSON-LD, не теряется из-за непустого raw HTML.
3. При повторении одного номера в нескольких представлениях создаётся один endpoint с несколькими доказательствами.
4. Телефоны нормализуются с проверкой страны/длины и классификацией: mobile, fixed, ambiguous, invalid. Стационарные и ошибочные не попадают в мобильный выбор; ambiguous не выдаётся за подтверждённый mobile.
5. Ссылки приглашения, share-ссылки, каналы, группы и боты не превращаются в обычного получателя по одной регулярке. Сохраняется причина исключения.

**LR-02, 5 SP.** Как оператор, хочу быть уверен, что найденный контакт принадлежит выбранной компании. Зависимость: LR-01.

Работы: общий resolver идентичности для каталогов, официальных сайтов и Firecrawl; нормализация русского/узбекского/латинского названия; независимые признаки адреса, телефона, бренда и домена. Общее название — слабый признак. Противоречащие телефон/адрес не игнорируются. Изменение телефона или несколько филиалов требуют разрешения противоречия, а не автоматической потери всех данных.

Приёмка:

1. Чужой сайт с общим названием «Стоматология» не получает корпоративное подтверждение.
2. Сайт с несколькими компаниями не отдаёт весь список телефонов одной карточке.
3. Конфликт сохраняет исходные свидетельства и понятную причину; ручная проверка не подменяется автоматическим согласием на отправку.
4. Один набор входных доказательств даёт одинаковое решение во всех маршрутах провайдеров.

### Этап 2 — доказать, что бесплатный сборщик нам подходит (High)

**LR-03, 5 SP.** Как владелец, хочу выбрать работающий локальный движок на измерениях. Зависимость финальной оценки: LR-01; подготовку набора можно вести до его завершения.

Испытать Scrapling и Crawl4AI на одних 15 публичных компаниях трёх ниш: стоматологии, салоны красоты, автосервисы, плюс воспроизводимые локальные страницы. Включить JS-контакты, отсутствие сайта, запрет обхода, дубли, общее название и отсутствие публичного Telegram. Одинаковый лимит страниц и времени, один экстрактор, раздельные HTTP/browser результаты. Никакой отправки сообщений в пилоте.

Приёмка:

1. Есть lockfile, проверенные релиз/commit, лицензии зависимостей и воспроизводимая установка на используемом Windows. Критические известные уязвимости релизного набора исключены либо блокируют выпуск.
2. Приведены реальные входы, журнал выполнения без секретов, ожидаемые и полученные контакты; «не запускалось» не считается тестом.
3. Зафиксированы время, peak RAM, страницы, сетевой трафик и причины пропусков. API/LLM/CAPTCHA/платный proxy не обязательны и не вызывались.
4. На детерминированных тестовых страницах извлечены все размеченные поддерживаемые контакты; ни один заранее размеченный чужой контакт не признан корпоративным.
5. Выбран один основной движок. Если Scrapling проигрывает по корректности, упаковке или стабильности, используется тот же интерфейс с Crawl4AI. Два постоянно работающих краулера не обязательны.

15 компаний — smoke-test выбора, не доказательство качества на всём рынке. Обещания скорости и стоимости из исследования заменяются этим отчётом.

### Этап 3 — сделать сбор фоновым и восстанавливаемым (Critical)

**LR-04, 8 SP.** Как оператор, хочу продолжать сбор после закрытия вкладки, обрыва сети и перезапуска компьютера. Зависимости: LR-01, LR-03.

Работы: отдельный локальный runner, ограниченные права и память/время; исходящий claim/heartbeat/result протокол; серверные leases и очередь; checkpoint плюс квитанции. Идемпотентность учитывает организацию, задачу, нормализованный URL, поколение lease и версию обработки. Просроченный исполнитель не перезаписывает новый результат.

Приёмка:

1. Закрытие вкладки не останавливает уже созданную задачу.
2. Kill процесса, рестарт и потеря ответа после принятого результата не приводят к дублю контакта или бесконечным повторным загрузкам.
3. Выключенный ПК отражается как «ожидает сборщик», с временем последнего heartbeat; это не успешное завершение.
4. Краулер не читает Bridge vault; его токен не позволяет разрешать Telegram-контакты, менять кампании или отправлять сообщения.
5. HTTP и браузер одинаково блокируют loopback, private/link-local IP, metadata, file URL и опасные перенаправления. Проверяются DNS/редиректы/браузерные подресурсы; защита только начального URL недостаточна.
6. Соблюдаются robots/ограничения источника, Retry-After, лимит домена и размер ответа. Отказ источника записывается без бесконечного обхода блокировок.
7. В режиме free_only сеть не обращается к платным API; текущие Telegram-сессия и привязка сохраняются.

### Этап 4 — расширить покрытие источников и честно управлять лимитами (Critical)

**LR-05, 5 SP.** Как оператор, хочу поиск контактов и для компаний без известного сайта. Зависимости: LR-01, LR-02, LR-04.

Два маршрута: известный сайт → главная/контакты/about/филиалы/допустимый sitemap; нет сайта → доступные публичные бизнес-карточки, каталоговые ссылки, импорт URL и поиск официального домена. Для каждого провайдера поиска отдельно установить доступность, условия, ограничения и цену. Бесплатный краулер не объявляется бесплатным глобальным поисковым индексом. Если подходящего бесплатного поиска нет, честно поддерживаем известные сайты и разрешённые каталоги с явным пробелом покрытия.

Приёмка:

1. Третий и последующие релевантные результаты больше не теряются из-за `.slice(0, 2)`; обход ограничен общей очередью кандидатов и бюджетом, а не повторением первых двух ссылок.
2. Доверенная ссылка из карточки каталога на официальный домен может попасть в проверку; домен не обязан входить в фиксированный список каталогов.
3. Найденный обычный телефон не завершает задачу «найти Telegram», пока остаются релевантные источники и бюджет.
4. В интерфейсе различаются: «сайт неизвестен», «источник запрещён/недоступен», «контактов на просмотренных страницах нет», «проверка ещё не закончена».
5. Нет угадывания username, перебора номеров, выгрузки участников чужих групп или извлечения скрытых личных контактов. Обрабатываются опубликованные бизнес-контакты с проверкой принадлежности.

**LR-06, 5 SP.** Как оператор, хочу, чтобы ограничение ресурсов не выдавало ложное «всё проверено». Исправление существующего серверного маршрута не зависит от нового краулера и входит в этап 1; распространение модели ожиданий на новый runner зависит от LR-04/LR-05.

Работы: `waiting_budget / waiting_runner / retry_at / partial / complete`; справедливое распределение лимитов; кеш успехов отдельно от временных отказов; просроченные данные повторно проверяются адресно. Существующее различение причин резервирования сохраняется — старую обобщённую ошибку не выдаём за всё ещё единственную диагностику текущего кода.

Приёмка:

1. Возобновление доступного бюджета выводит задачу из ожидания; вчерашний `limited` не блокирует её ещё на сутки без причины.
2. `sources_exhausted` выдаётся только для исчерпанного доступного набора источников, а не из-за нехватки бюджета или отсутствия исполнителя.
3. Повторный поиск одной компании использует свежие допустимые доказательства; данные и права не смешиваются между организациями.
4. Зарезервированные и подтверждённо потраченные кредиты показаны раздельно. Неизвестный платный исход проходит сверку с провайдером при наличии такой возможности, иначе остаётся неизвестным без слепого повтора.
5. Пользователь видит расход, остаток и следующий шаг; включение платного резерва требует явного выбора в рамках заданных лимитов.

### Этап 5 — собрать один корректный список получателей (Critical)

**LR-07, 5 SP.** Как оператор, хочу одну карточку контакта со всеми источниками и историями поисков. Зависимости: LR-02, LR-06.

Работы: разделить компанию/филиал, endpoint и вхождение в поиск; объединять доказательства без потери происхождения. Одинаковый номер у филиалов не доказывает, что это одна организация; разные canonical keys не всегда доказывают конфликт. Выбор представителя группы учитывает действующую проверку и её область, а не только свежесть карточки.

Приёмка:

1. Один и тот же подтверждённый контакт из нескольких поисков не дублируется в одной кампании.
2. Проверка из другого запуска учитывается только при совпадении компании, endpoint, аккаунта и актуальности; основание на одну компанию не переносится автоматически на другую.
3. Ручной конфликт/отказ/«не связываться» сохраняется и не снимается очередным парсингом.
4. Миграция добавочная; dry-run показывает до/после и конфликты; история и старые источники остаются доступны.

**LR-08, 5 SP.** Как оператор, хочу одной кнопкой выбрать подходящие контакты из всех ниш и запустить их проверку. Зависимость: LR-07.

Работы: один серверный источник списка и счётчиков для верхней аудитории, нижней карточки и кампании. Кнопки «Выбрать мобильные и username», «Проверить в Telegram», «Выбрать готовых». Сохраняем имеющийся массовый выбор, исправляем семантику и согласованность; не реализуем его повторно с нуля.

Приёмка:

1. Выбор охватывает весь текущий фильтр, а не только видимую страницу, с серверным подтверждением списка/лимита. Существующий лимит аудитории 500 не означает кампанию на 500.
2. Отдельно показаны «выбрано», «принадлежность не подтверждена», «ожидают Telegram», «подтверждены в Telegram», «готовы к автоотправке».
3. Для каждого исключения есть причина и действие; номер без подтверждения не исчезает, но не отмечается готовым.
4. Выбор, текст и загруженные материалы не сбрасываются при polling/обновлении статуса; повторный предпросмотр отражает изменения актуальных допусков.
5. Верхнее и нижнее представления совпадают при одинаковых фильтре и версии данных; устаревший ответ не откатывает свежий.

### Этап 6 — проверить Telegram и завершить путь до кампании (Critical)

**LR-09, 5 SP.** Как оператор, хочу настоящую фоновую проверку выбранных публичных корпоративных контактов. Зависимости: LR-07, LR-08.

Работы: перевести существующий возобновляемый браузерный цикл в серверную очередь заданий Bridge, сохранив peerRef, account binding, срок действия и квитанции. Номер без username проверяется существующим поддерживаемым путём. Нет нового входа в аккаунт для каждого запуска.

Приёмка:

1. Проверка не требует открытой страницы; прогресс и причины доступны после перезагрузки.
2. Обычный пользователь, бот, канал, группа, удалённый аккаунт, privacy_or_missing и временный отказ дают разные результаты.
3. Истёкшая проверка, смена аккаунта и потеря свежего heartbeat не создают ложное состояние готовности.
4. FloodWait/ограничение Telegram ставит очередь на ожидание; нет смены аккаунтов или обхода лимита для продолжения.
5. Не подтверждённая принадлежность блокирует автоматическое использование контакта; локальный peer не раскрывается как сессия/секрет в браузере или логах.

**LR-10, 5 SP.** Как оператор, хочу увидеть точных получателей, текст, изображение и причины блокировки до запуска. Зависимости: LR-08, LR-09.

Работы: довести существующий server preflight и финальное подтверждение, а не снять его проверки. Готовность требует актуального подключённого аккаунта, подходящего peer, доказательств принадлежности, действующего основания отправки, отсутствия DNC/дублей и доступного лимита. Выбор основания в форме не создаёт его для всех контактов. Общий документ можно применять только к явно перечисленным компаниям/области, подтверждаемым этим документом.

Приёмка:

1. Пользователь видит точный итог: например, из N выбранных X готовы, Y ожидают основания/проверки, Z исключены; сумма и список подтверждаются сервером.
2. Изменение текста, изображения, аккаунта или списка делает прежний предпросмотр неактуальным; нужен новый. Текст можно редактировать и при временно отключённой отправке.
3. Сохраняются текущие ограничения 50 получателей на кампанию, 30 отправок на UTC-сутки и интервал не менее 120 секунд; они не являются обещанием безопасности от ограничений Telegram.
4. Pause/Stop, отзыв основания, DNC и потеря соединения проверяются перед следующей отправкой. Повторное нажатие запуска не создаёт вторую кампанию.
5. Неопределённый результат отправки не повторяется автоматически: сначала сверка доступных квитанций/состояния или ручное разрешение. Не обещаем exactly-once на одной локальной отметке.
6. Отдельный живой тест — только после явного согласования получателя и точного сообщения пользователем. Факт принятия Telegram и отображение статуса проверяются отдельно от ответа получателя или маркетинговой конверсии.

### Этап 7 — восстановить старые результаты и выпустить обновление (High)

**LR-11, 5 SP.** Как владелец, хочу получить улучшения в существующих поисках без потери данных и повторной привязки Telegram. Зависимости: LR-01–LR-10.

Работы: dry-run исторической выборки; сначала выбранные пользователем и ранее пропущенные из-за ограничений компании, затем остальные. Новая обработка не переписывает неизвестные исходы старых платных запросов. Совместимые добавочные миграции, версии схемы и флаги по компонентам. Сравнение нового маршрута в теневом режиме не включает реальную отправку.

Приёмка:

1. Поэтапный rollout: локальные fixtures → 15 компаний → 50 существующих компаний → расширенная размеченная выборка, затем общий режим. Для каждого прохода известны лимиты и результаты.
2. Собраны точность принадлежности, полнота извлечения на размеченных доступных страницах, покрытие загрузки, число разрешённых Telegram peer, число реально допущенных к отправке, дубли, задержка очереди и затраты.
3. Стартовые цели для размеченной полевой выборки: точность корпоративной привязки >=98%, полнота извлечения явно опубликованных поддерживаемых контактов >=90%. Всегда указываются знаменатель, состав выборки и ошибки; маленький пилот не подтверждает эти показатели для всего рынка. Все известные ложные допуски исправляются или блокируют соответствующий маршрут.
4. На негативных регрессиях — ноль чужих контактов, ошибочно допущенных к кампании; ноль отправок без основания, ноль дублей при тестовых повторах. Отсутствие публичного контакта не искусственно улучшает или ухудшает метрику извлечения.
5. Проверены миграция, восстановление после сбоя, ограничение ресурсов и откат флага нового сборщика. Откат не удаляет контакты, историю или сессию.
6. Выпуск проходит существующий guard совмещённого Pages/Lead Radar релиза; проверяются commit, артефакты и совместимость Worker/Bridge. Не допускаем повторного затёртого интерфейса из другого checkout.

## 7. Что будет означать «корректно работает»

Пользователь задаёт нишу/город, видит реальный ход работы и ограничения источников. Все найденные публичные бизнес-контакты имеют доказательства; чужие, стационарные, неоднозначные и неподходящие Telegram-типы не маскируются под готовых получателей. Из всех поисков можно одним действием собрать выборку, запустить фоновую проверку, увидеть точные причины исключений, проверить содержание и явно запустить допустимую кампанию.

**Не обещаем:** Telegram у каждой компании; обязательные 50 получателей на любую нишу; раскрытие приватных номеров; отсутствие ограничений Telegram; гарантированную доставку или продажи. **Обязуемся проверять:** отсутствие известных потерь в нашем парсере, честные состояния, устойчивое возобновление, доказуемую принадлежность и отсутствие неразрешённых/повторных отправок.

Первый инженерный шаг — LR-01/LR-02, независимое серверное исправление LR-06 и эталонные страницы. Затем короткий LR-03, выбор движка и подключение через LR-04. Дальнейшие решения о библиотеке принимаются по измерениям этого конкретного пилота.
