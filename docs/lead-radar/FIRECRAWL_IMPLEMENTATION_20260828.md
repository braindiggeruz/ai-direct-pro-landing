# Firecrawl: реализация и безопасное включение

Дата: 28 августа 2026. Статус: серверный MVP реализован и проверен; доступ к API подтверждён, готовится выключенный production-релиз.

Проверка ключа через read-only `GET /v2/team/credit-usage`: 1 025 доступных кредитов, 1 000 plan credits. Search/Map/Scrape не запускались. Название тарифа и настройка автодоплат этим ответом не подтверждены; ключ хранится вне репозитория и не публикуется.

## Что готово

- Cloud API v2 через серверный HTTP, без новой зависимости SDK и без скрытых повторов.
- Поиск официального домена для новых компаний без сайта. Search даёт только кандидатов: совпадение названия без географии/телефона не подтверждает принадлежность.
- Map + максимум четыре страницы. Нет массового Crawl, Agent, LLM-JSON, PDF или browser actions.
- Рендеренный HTML и rawHtml используются только в памяти; в D1 остаются компактные доказательства, все допустимые Telegram-кандидаты, URL, хеш содержимого, время и ID провайдера при наличии.
- Разметка `Dentist`/`MedicalClinic` распознаётся наряду с Organization/LocalBusiness. Корпоративный endpoint больше не перекрывается неподтверждённым личным контактом при объединении результатов.
- `onlyMainContent:false`, `onlyCleanContent:false`, `skipTlsVerification:false`, `maxAge:0`, `storeInCache:false`, `parsers:[]`. Не заявляем, что отключение кэша означает нулевое хранение у провайдера.
- Проверяются публичный URL, DNS и robots.txt; запросы с query-параметрами, credentials, приватными адресами, login/admin и файлами исключаются. Сообщённый провайдером чужой URL отклоняется. `sourceURL` не всегда доказывает конечный URL: реальные перенаправления нужно включить в живой пилот.
- Личные записи остаются выключенными существующим флагом. Firecrawl не получает Telegram-сессию, пароль, cookies или текст рассылки.
- Извлечение не выставляет `messageable:true`. DNC, основания, актуальность, квоты и защита от повторных отправок сохранены. Bridge и sender не переделывались.

## Бюджет и восстановление

Три новые изолированные таблицы в `0049_lead_radar_firecrawl.sql`:

- `lead_radar_firecrawl_requests`: резерв затрат и результаты операций;
- `lead_radar_firecrawl_control`: остановка при ошибке авторизации/баланса, общий backoff;
- `lead_radar_firecrawl_reports`: безопасная диагностика по компании и поиску.

Резерв создаётся одним `INSERT…SELECT` до API-вызова, с проверкой квот, владельца lease, поколения lease и отсутствия suppression компании. Уникальность `(org_id, request_key, attempt)` не даёт двум доставкам оплатить одну операцию.

Лимиты первого релиза:

- максимум 200 зарезервированных кредитов за UTC-сутки для этой интеграции;
- по умолчанию 140 на поиск (разрешается настроить только в пределах 200);
- 14 на домен/организацию/UTC-сутки;
- 7 на компанию в одном задании;
- не более двух новых API-вызовов за доставку Queue;
- не более двух незавершённых вызовов и десяти новых запросов в минуту для интеграции.

Операции Search резервируют 2 кредита, Map/Scrape — 1. Это консервативный внутренний учёт базовых операций, **не сверенный счёт Firecrawl**. Он не учитывает чужие приложения/ручные вызовы в том же аккаунте. Тариф и Smart Upgrade проверяются владельцем перед пилотом.

Завершённые операции используются повторно без обращения к провайдеру. Большая обработка продолжается последующими доставками существующей очереди. Вся цепочка не зависит от вкладки. Сохраняются текущие три попытки бизнес-задания; длительный outage/rate limit может завершиться частичным результатом, а не бесконечным ожиданием.

Неизвестный исход submission/таймаут не повторяется автоматически. Резерв не возвращается при ошибке. HTTP 429 допускает одну дополнительную попытку после backoff, с новым резервом. Ошибки 401/403/402 открывают сохраняемый circuit breaker до проверки оператором; наступление новых суток его не снимает.

Короткоживущие результаты удаляются через 24 часа ограниченным cron-cleanup, независимо от флага Firecrawl. Суммы/статусы остаются: удаление данных или истечение TTL не должно отменять расходы и разрешать повторную оплату старого задания.

## Интерфейс

Под воронкой поиска добавлена раскрывающаяся секция «Обогащение сайтов · Firecrawl». Кнопка «Показать диагностику» только читает:

`GET /api/admin/lead-radar/searches/:searchId/enrichment`

Маршрут защищён owner-role и tenant-scoped проверкой существования поиска. В нём нет ключа, raw HTML или автоматического запуска платных задач. Видны страницы, корпоративные контакты, shadow/fallback, резерв кредитов и причины отказа/частичного результата.

## Проверки

- `npm run test:firecrawl`: API/бюджет/безопасность, интеграция с настоящей SQLite D1-фикстурой и очередью, совместимость схемы.
- `npm run test:lead-radar`: существующий функционал, sender, кампании, evidence, queue/release guards.
- В `lead-radar-d1-budget.test.ts` проверены четыре страницы с известным и отсутствующим сайтом: 27/27/36 и 27/27/39 D1 statements по доставкам. Плюс резерв 9 на outer Worker и heartbeat: максимум 48/50.
- Typecheck, ESLint, сборка приложения и SEO-аудит.
- `wrangler deploy --dry-run --config wrangler.automation.toml` проверяет сборку Worker без публикации.
- Доступ к живому API и баланс подтверждены. Парсинг реальных сайтов, настройки автодоплат, прирост количества контактов, работа при реальной задержке и списания **ещё не проверены**.

## Порядок выпуска — важно

1. Проверить актуальную ветку и сохранить чужие изменения. Не откатывать AGENTS, Bridge или SEO.
2. Выполнить тесты и dry-run. Оставить `LEAD_RADAR_FIRECRAWL_ENABLED=false`, `MODE=off`, allowlist пустым.
3. **Сначала опубликовать новый Worker и Pages с выключенным Firecrawl. Потом применить 0049.** Старая версия строгого schema-аудита не знает эти таблицы; миграция до обновления кода может остановить старый Lead Radar.
4. Проверить только целевую D1 `gptbot-ai-drafts`, binding `GPTBOT_DRAFTS_DB`, ID `97ef0372-d937-406f-8871-755368d9afff`. Изучить ledger до изменений. Не применять все накопленные миграции вслепую: в репозитории есть альтернативные ветки миграций.
5. Применить ровно `migrations/0049_lead_radar_firecrawl.sql`, зарегистрировать её в `d1_migrations` и проверить base fingerprint + таблицы расширения. Это аддитивная миграция; никакого DROP/пересоздания.
6. Добавить `FIRECRAWL_API_KEY` **как secret Worker `gptbot-automation`**, не в Pages/VITE/Git/чат. Например, интерактивно: `npx wrangler secret put FIRECRAWL_API_KEY --config wrangler.automation.toml`. Не передавать значение аргументом командной строки.
7. Владелец подтверждает отсутствие нежелательных автодоплат и лимит пилота до 200 кредитов. API-ключ уже предоставлен через приватный файл и проверен; ссылка на кабинет не используется как секрет.
8. Включить только одну явную org в `LEAD_RADAR_FIRECRAWL_ALLOWED_ORGS`, `ENABLED=true`, `MODE=shadow`. Создать **один новый** контрольный поиск до 20 компаний. Не запускать переобработку истории и не отправлять сообщения.
9. Проверить исходные сайты и корпоративные контакты вручную, сравнить с direct fetch, сверить расходы с кабинетом. Проверить bot/channel/group, тёзок, редиректы, robots, частичный результат, возобновление и ошибки 402/429.
10. Только после приёмки перевести эту org в `fallback`. Любые реальные сообщения — отдельное подтверждение владельца адресата/текста.

Остановить новые платные запросы: `ENABLED=false`/`MODE=off`, затем обновить Worker. Уже принятые провайдером операции могут завершиться. **Не откатывать код на версию, которая не знает optional schema**, и не удалять таблицы для «возврата бюджета».

После исправления ключа/баланса сброс circuit breaker — отдельное узкое операторское действие над строкой `id='account'`, только после проверки причины. UI не сбрасывает его сам.

## Что следует после измеренного пилота

- P0: разметка 20 реальных компаний и сравнение стоимости/полноты.
- P6: явная выборочная переобработка существующих карточек с предварительной оценкой. В этом MVP обогащаются новые поиски, автоматически историю не трогаем.
- P7: отдельная цель по контактам и расширенный резерв 300–500 компаний. Лимит текущей выдачи/кампании 50 не менялся.
- Batch/Crawl/webhook не используются; их отдельный lifecycle и HMAC нужны только при масштабировании, не для текущего последовательного Scrape.
- Подключение API не создаёт контакты там, где их нет, и не гарантирует 50 получателей или отсутствие ограничений Telegram.
