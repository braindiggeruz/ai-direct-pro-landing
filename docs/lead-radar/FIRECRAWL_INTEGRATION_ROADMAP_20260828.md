# Firecrawl × Lead Radar — план интеграции

Дата исследования: 28 августа 2026. Статус: предложение к реализации, не выполненная интеграция.

В этом исследовании не вызывался оплачиваемый Firecrawl API, не создавались ключи и подписки, не запускались рассылки и не менялся production-код.

## Решение

Рекомендуется Firecrawl Cloud API v2 как дополнительный транспорт для поиска и чтения публичных сайтов. Существующие OSM discovery, проверка принадлежности компании, правила контактов и отправитель Worker → Bridge сохраняются.

MCP полезен для исследовательской работы агента, но production-интеграция должна работать через серверный HTTP API и очередь независимо от Codex и открытой вкладки. Self-hosting не является первым этапом: собственный стек требует отдельного обслуживания, а облачные и open-source возможности не полностью совпадают. [Cloud vs open source](https://docs.firecrawl.dev/contributing/open-source-or-cloud).

Firecrawl не предоставляет гарантированный список из 50 готовых Telegram-получателей. Его результат — содержание страниц и кандидаты в контакты. Проверенность, релевантность и допустимость обращения — отдельные решения Lead Radar.

## 1. Что проверено

### Кабинет

Предоставленная ссылка открывает авторизацию Firecrawl. В доступном браузере нет вошедшей сессии. Тариф, остаток кредитов, API-ключ и настройка Smart Upgrade этого аккаунта не проверены. Ссылка на кабинет не заменяет API-ключ.

### Текущий код

| Участок | Фактическое поведение | Что требуется |
|---|---|---|
| `functions/platform/lead-radar/queue.ts`, `processEnrichment` | Если `lead.website` отсутствует, сохраняет `no_website` и завершает задание | Этап поиска кандидатов в официальные домены до окончательного отказа |
| `functions/platform/lead-radar/sources.ts`, `fetchText` | Обычный HTTP fetch, 5 секунд на запрос, ограниченные перенаправления | Дополнительный путь для динамических/медленно отвечающих публичных сайтов |
| `sources.ts`, `sameOriginLinks` | Берёт максимум две подходящие ссылки с главной | Приоритетный выбор контактных страниц через Map, с общим лимитом |
| `sources.ts`, `verifyCompanyWebsiteBinding` | Сопоставляет ожидаемый телефон или название | Сохранить проверку и усилить конфликтами города/адреса и одноимённых компаний |
| `sources.ts`, `classifyTelegramContact` | Классификация по признакам страницы; неизвестные и личные контакты не становятся автоматически доступными | Сохранить консервативный допуск; не доверять утверждению LLM «это бизнес» |
| `sources.ts`, `enrichCompanyWebsiteWithBudget` | Выбирает один `telegramContact`; human ранжируется выше business | Хранить все обнаруженные кандидаты, отдельно выбирать допустимый корпоративный контакт |
| `queue.ts`, `processDiscovery` | Fan-out ограничен `min(50, desiredCount)` | Отделить бюджет исходных компаний от цели по контактам |
| `queue.ts`, `LeadRadarQueueDependencies.enrichWebsite` | Уже существует подменяемый обогатитель | Использовать эту точку, не переписывать всю очередь |
| `workers/automation-worker.ts` | Вызывает существующий consumer; сейчас передаёт только флаг personalDataEnabled | Подключить серверный адаптер и его настройки в worker |

Это ограничения и точки интеграции, подтверждённые чтением кода. Эффект Firecrawl на реальной выборке ещё не измерен. Ошибка `source_unavailable` сама по себе не доказывает конкретную первопричину.

## 2. Возможности Firecrawl и выбор для MVP

| API | Назначение в Lead Radar | Решение |
|---|---|---|
| Search | Найти кандидатов в официальные сайты по названию и городу | Только для отсутствующего/сомнительного домена; сначала без автоматического scraping всех результатов |
| Map | Получить URLs сайта и выбрать страницы контактов/команды | Один ограниченный вызов на домен, без обхода всего интернета |
| Scrape | Прочитать выбранную публичную страницу с рендерингом JavaScript | Основной транспорт fallback; HTML/links и при необходимости rawHtml |
| Batch Scrape | Асинхронно обработать заранее выбранные URLs | Для масштабирования; хранить ID задания и забирать результат из backend |
| Crawl | Обход сайта по ссылкам | Не нужен по умолчанию; только ограниченный резервный режим |
| JSON extraction | Дополнительно извлечь структуру по JSON Schema | Опционально после обычного извлечения; отсутствующее значение — null |
| Agent / Interact | Автономные действия и браузерные сценарии | Не включать в первый релиз: лишняя свобода действий, стоимость и сложность проверки |

Подтверждение возможностей: [Search](https://docs.firecrawl.dev/features/search), [Map](https://docs.firecrawl.dev/features/map), [Scrape](https://docs.firecrawl.dev/features/scrape), [Batch Scrape](https://docs.firecrawl.dev/features/batch-scrape), [JSON mode](https://docs.firecrawl.dev/features/llm-extract).

## 3. Архитектура

```text
OSM / имеющиеся компании
          ↓
Есть подтверждённый домен?
  нет → Search → кандидаты доменов → проверка принадлежности
          ↓
Обычный загрузчик / Firecrawl fallback
          ↓
Map при необходимости → до 4 выбранных страниц
          ↓
HTML, реальные ссылки, контекст, сведения о получении страницы
          ↓
Наше извлечение → список кандидатов → проверка принадлежности и типа
          ↓
Релевантность офферу + допустимость контакта + исключение дублей/отказов
          ↓
Предпросмотр и явное подтверждение владельца
          ↓
Существующий Worker → локальный Telegram Bridge
```

Firecrawl никогда не получает Telegram-сессию, 2FA, cookies админки, приватную переписку или внутренние данные кампании. Ему передаются только необходимые публичные поисковые запросы и URLs.

## 4. Роадмап

### P0 — контрольная выборка и бюджет

- Вручную разметить 20 компаний: известный рабочий сайт, JS-сайт, сайт без Telegram, официальный бизнес-контакт, бот/канал, одноимённая чужая организация, временная ошибка.
- Зафиксировать исходные показатели direct fetch на этой же выборке.
- Подтвердить доступ к Firecrawl, тариф, баланс и настройки автоматических доплат.
- Предложенный лимит пилота — 200 кредитов; любые вызовы только после подтверждения подключения и этого бюджета.
- На пилоте никакой рассылки и автоматической массовой переобработки истории.

Приёмка: известны исходные данные, ожидаемые результаты, лимит затрат и условия остановки.

### P1 — серверный адаптер и защита затрат

- Добавить модуль `functions/platform/lead-radar/firecrawl-client.ts` с API v2, валидаторами запросов/ответов, таймаутами и нормализованными ошибками.
- Ключ хранить в Cloudflare Worker secret, не в `VITE_*`, клиентском JS, Git, URL или диагностических логах.
- Предлагаемые флаги: `LEAD_RADAR_FIRECRAWL_ENABLED`, `LEAD_RADAR_FIRECRAWL_MODE=off|shadow|fallback`, лимиты на запуск/сутки/домен и разрешённую организацию. Это проектируемые настройки, их пока нет.
- До запроса атомарно резервировать кредитный бюджет с учётом одновременных задач; после результата сверять фактический расход. Не освобождать неизвестный расход только по клиентскому таймауту.
- Отдельно учитывать 401/403 провайдера, 402, 429 и ошибки целевого сайта в metadata. При 402 останавливать платный этап; при 429 — отложенный ограниченный повтор.
- Глобальный выключатель возвращает старый путь; ошибка Firecrawl не блокирует SEO-сообщения общей очереди.

Приёмка: выключенный флаг даёт ноль вызовов Firecrawl; параллельные задания не обходят бюджет; ключ отсутствует в frontend и логах.

### P2 — поиск официального сайта

- До текущего `no_website` запускать ограниченный Search: название, город, ниша; максимум один основной запрос и отдельно разрешённая попытка уточнения.
- Поисковые сниппеты использовать только для выбора кандидатов, не как доказательство принадлежности Telegram.
- Сопоставлять страницу с публичным телефоном, названием, географией и адресом. Противоречия требуют ручной проверки.
- Каталог может помочь найти домен, но не становится официальным сайтом компании.
- Не позволять первому совпадению названия автоматически подтверждать одноимённую компанию в другом городе.

Приёмка: найденные домены воспроизводимо связаны с компаниями; неправильные домены из отрицательных тестов не подтверждаются.

### P3 — извлечение без потери контактов

- На подтверждённом домене выбирать главную, контакты и до двух дополнительных релевантных страниц; не расходовать бюджет на весь блог.
- Явно ставить `onlyMainContent: false`: стандартная настройка исключает шапку и подвал, где может находиться контакт. `onlyCleanContent` не включать для доказательного извлечения.
- Для JSON-LD использовать rawHtml там, где очищенный HTML его теряет; проверить на фикстурах, а не предполагать сохранение script-блоков.
- Явно сохранить проверку TLS (`skipTlsVerification: false`), лимиты ответа, доменов, перенаправлений и допустимых типов документов.
- Сохранять исходный и финальный URL, provider job ID, хеш контента, время получения, известную свежесть источника и факт использования кэша. Получение кэшированного ответа не продлевает автоматически проверку контакта.
- Извлекать все Telegram-кандидаты, а не только один наиболее высоко ранжированный.

Для этих настроек основание — [Scrape API](https://docs.firecrawl.dev/api-reference/endpoint/scrape). Конкретный формат ответа закрепить контрактными тестами.

Приёмка: контакт из подвала, страницы контактов и JSON-LD не теряется; неизвестный или старый источник не становится свежепроверенным автоматически.

### P4 — доказательства, тип контакта и релевантность

- Firecrawl — транспорт. `sourceUrl` остаётся адресом страницы компании; `sourceType=company_website` допустим только при фактическом first-party источнике, а сведения о провайдере хранятся отдельно.
- Для каждого кандидата нужны точная ссылка, окружающий текст/подпись, компания, тип, дата, доказательство принадлежности и причина допуска/исключения.
- LLM-JSON — предложение извлечения, не разрешение на отправку. Проверять наличие ссылки в полученном источнике. Не позволять модели придумывать номера, людей, роли, usernames и доказательства.
- Содержание сайта считать недоверенным: инструкции со страницы не могут менять бюджет, запускать действия или обращаться к секретам.
- Не перебирать телефонные номера в Telegram. Не искать скрытые личные контакты. Личные данные не включать новым флагом без отдельного решения.
- Перед отправкой сохраняются существующие серверные проверки: допустимый тип, привязка компании, актуальность, основание обращения, отсутствие отказа и повторов.
- Под стоматологический оффер отдельно оценивать соответствие клинике и наблюдаемые проблемы сайта. Отсутствие найденного сайта не означает, что сайта нет; наличие Telegram не означает согласия на рекламу.

Приёмка: ноль автоматически разрешённых ботов, каналов, групп, чужих компаний и неподтверждённых личных аккаунтов в контрольном наборе.

### P5 — фоновые задания и восстановление

- Использовать существующий consumer и точку `enrichWebsite`; расширить контракт для отложенного результата, если используется Batch/Crawl.
- Отдельно сохранять состояние заявки провайдеру, его ID, выбранные URLs и версию извлечения. Для новых состояний/таблиц — аддитивная миграция и обновлённые schema contracts, без пересоздания SEO-таблиц.
- Не держать один браузерный HTTP-запрос до окончания всего обхода.
- После принятия задания получать статус из backend; при повторной доставке очереди продолжать старое задание, а не создавать новое платное.
- Таймаут отправки запроса с неизвестным результатом — отдельное состояние для сверки; не обещать exactly-once у внешнего API без документированной гарантии.
- Webhook необязателен для MVP. При его добавлении: HMAC-SHA256 по исходным байтам, проверка длины и формата подписи, постоянное время сравнения, привязка job ID к tenant, защита от повторов. [Webhook security](https://docs.firecrawl.dev/webhooks/security).
- Сбой webhook компенсируется серверной сверкой; готовность не зависит от вкладки.

Приёмка: перезапуск Worker и повтор очереди не создают повторного обогащения/расхода при известном provider ID; данные одной организации недоступны другой.

### P6 — интерфейс и ограниченная переобработка

- Добавить действие «Обогатить выбранные компании» с оценкой числа страниц и верхней границы расходов.
- Показывать отдельно: сайт найден, принадлежность подтверждена, сайт прочитан, Telegram найден, контакт проверен, допущен к кампании.
- Показывать отказ по бюджету, очередь провайдера, ошибку страницы и отсутствие контакта как разные состояния.
- Переобрабатывать только выбранные карточки без свежего успешного результата; не повторять все прошлые поиски.
- Сначала провести пилот в shadow-режиме и сравнить результат со старым способом; выводы не открывают отправку автоматически.

Приёмка: владелец видит результат, доказательства и расходы, а не бесконечный индикатор ожидания.

### P7 — расширение до 50 подходящих контактов

- Только после успешного пилота разделить `desiredVerifiedContacts` и `maxCandidateCompanies` в серверной модели и UI.
- Сохранять ограниченный резерв до 300–500 кандидатов и обрабатывать порциями; лимит кампании 50 не изменять.
- Дедупликация по компании, домену и нормализованному Telegram endpoint между запусками; все ключи tenant-scoped.
- Останавливаться при достижении цели, бюджетного лимита или исчерпании источников.
- На первом production-пилоте оставить географию выбранного города; несколько городов и объединение запусков — следующий измеряемый этап.

Приёмка: честный итог «17 из 50» допустим. Неподтверждённые контакты не добавляются ради достижения числа.

### P8 — выпуск и проверка рассылки

- Unit/contract: ссылка в footer, JS-контент, относительные ссылки, редиректы, stale cache, неверный JSON, SSRF, секреты и ограничения бюджета.
- Negative: бот, канал, группа, чужой домен, личный контакт, prompt injection, DNC и дубли.
- Recovery: 402, 429, таймаут после submission, повтор webhook/Queue, перезапуск Worker, provider outage.
- Regression: существующие Lead Radar/Bridge тесты и проверки SEO; текущие тарифы/публичные SEO-страницы не редактировать.
- Deployment: shadow → ограниченный fallback для одной организации → расширение по метрикам. Выключение Firecrawl не отключает Bridge и не меняет SEO.
- Тестовая отправка только на свой/явно согласованный аккаунт, после отдельного утверждения адресата и текста. Реальная рассылка — отдельное действие владельца.

Приёмка: измеренный прирост полезных контактов, ноль ошибочных автоматических допусков в контрольной выборке, сохранённые ограничения затрат и отсутствие SEO-регрессий.

## 5. Стоимость и ограничения

На публичной странице Free указан с 1 000 кредитов/месяц; Hobby — 5 000. Официальный материал указывает $19/месяц для Hobby; Pricing показывает $16/месяц при годовой оплате. Это не подтверждение условий конкретного аккаунта. [Pricing](https://www.firecrawl.dev/pricing), [официальные цены с помесячной оплатой](https://www.firecrawl.dev/blog/best-enterprise-scraping-services).

По Billing: базовый Scrape — 1 кредит/страницу, Map — 1/вызов, Search — 2 за каждые начатые 10 результатов; scraping результатов оплачивается дополнительно. JSON extraction добавляет 4/страницу. [Billing](https://docs.firecrawl.dev/billing).

Наш расчёт, не коммерческое предложение: один Search до 10 результатов + один Map + четыре обычные страницы = 7 кредитов на компанию.

| Кандидаты | Базовый расчёт | С резервом 30%, округлённо |
|---|---:|---:|
| 20 | 140 | 182 |
| 50 | 350 | 455 |
| 300 | 2 100 | 2 730 |
| 500 | 3 500 | 4 550 |

Исключены JSON, ZDR, дополнительные домены, дополнительные поиски и другие платные опции. Реальный расход будет зависеть от ранней остановки, наших кэшей и повторов. При четырёх JSON-страницах на компанию базовая оценка возрастает с 7 до 23 кредитов.

Нельзя считать HTTP-ошибку целевой страницы бесплатной. У Batch/Crawl списания могут появляться после принятия задания. Не оставлять Crawl без явного маленького `limit`; не включать Smart Upgrade без решения владельца. Внутренний лимит должен учитывать уже отправленные незавершённые запросы. [Правила списания и Smart Upgrade](https://docs.firecrawl.dev/billing).

Free: 2 одновременных браузера и 10 запросов Scrape в минуту; Hobby: 5 и 100 соответственно. Ограничения общие для команды, а не отдельные на каждый ключ. Данные старших тарифов в Pricing и Rate Limits местами расходятся — фактические лимиты аккаунта нужно подтвердить, а concurrency сделать настраиваемой. [Rate Limits](https://docs.firecrawl.dev/rate-limits).

## 6. Безопасность и данные

- Поддержать robots-политику и её диагностику. Firecrawl не используется для обхода запрета, авторизации или доступа к закрытой информации.
- Не отправлять в провайдер URL с секретами и приватными query-параметрами, пользовательские cookies, коды и логи.
- Отключение `storeInCache` не равно нулевому хранению. Доступность и стоимость ZDR согласуются отдельно; минимизировать сохранённые snippets и сроки хранения в Lead Radar. [Параметры хранения](https://docs.firecrawl.dev/api-reference/endpoint/scrape).
- Не исполнять HTML провайдера в админке; отображать очищенный текст и проверенные ссылки.
- Не расширять существующее разрешение на личные данные; публичные бизнес-источники остаются основой.

## 7. Метрики и условия следующего этапа

Измерять на одинаковой контрольной выборке:

1. Долю найденных и правильно сопоставленных официальных сайтов.
2. Долю разрешённых сайтов, содержание которых действительно получено.
3. Полноту извлечения известных публичных Telegram-ссылок.
4. Точность допуска бизнес-контактов и причины исключения.
5. Число новых подходящих получателей, а не число HTTP 200.
6. Кредиты на сайт и на один новый допустимый контакт.
7. Время обработки и восстановление после сбоя.

Целевой тестовый порог полноты можно установить не ниже 90% известных доступных ссылок; это требование к контролируемым тестам, не обещание охвата всего интернета. Для ошибочных автоматических допусков порог в контрольной выборке — ноль.

Следующее практическое действие: подтвердить доступ/бюджет, затем реализовать выключенный по умолчанию адаптер и провести 20-компанейный пилот. Массовое расширение и первая реальная рассылка не входят в исследование и требуют прохождения критериев выше.
