# Lead Radar — приоритетный план исправления (аудит 2026-08-30)

Принципы: точечные контракты и состояние, не перепись. Каждый этап закрывает подтверждённые находки из FULL_AUDIT.md (ссылки QR-*/DS-*/TG-*/CP-*).
Отдельно выделен минимальный набор для надёжной первой кампании (MVP-гейт).

## Этап 0 — синхронизация runtime (без кода)

Цель: чтобы существующие исправления начали работать там, где крутится поиск.

| Задача | Решает | Пользовательский эффект | Действия |
|---|---|---|---|
| 0.1 Деплой automation Worker на HEAD `0ddce6c` | QR-2, QR-3, частично QR-6 | поиск перестаёт висеть за бюджетной парковкой; сайты после даунтайма снова обрабатываются | `git` — уже в HEAD; прогнать `npm run test:firecrawl`, `test:lead-radar-contacts`; deploy `gptbot-automation` (wrangler.automation.toml без изменения bindings/flags); post-check: версия/время деплоя |
| 0.2 Активация Jina (опция, отдельное решение) | DS-1 частично (fallback скачивания) | больше страниц контактов переживает 521/5xx | Установить `LEAD_RADAR_JINA_ENABLED=true` на **Pages и Worker одновременно** (переменная читается в contact-source-worker, который исполняется Worker'ом; без Worker-флага не активна). Проверить актуальные условия r.jina.ai. Не решает Firecrawl-search зависимость |

Разрешения: 0.1 — production-деплой (согласовать, внешних побочных эффектов не создаёт). 0.2 — внешний сервис, оценить стоимость/лимиты перед включением.

Критерии приёмки 0.1: после деплоя у поиска с бюджетно-припаркованным job'ом пополняется пул (наблюдение на одном новом поиске, не replay старых); в логах нет новых `worker_failure` от retry-delay.
Rollback: предыдущая версия Worker (задеплоенный код совместим со схемой D1).

## Этап A — контракты очередей (устойчивость воронки)

1. **A1. Возрождение contact-resolution job** (QR-1): `ensureContactResolutionJob` обновляет dead_letter строку (кроме terminal-причин вида robots/invalid) или deadLetterJob чистит idem-ключ для purpose=contact_resolution. Миграция не нужна. Тест: dead-letter → новое завершение enrichment пересоздаёт job. Сложность: S.
2. **A2. Возврат батча при провале fanout** (QR-4): unreserve/reserve-after-persist в contact-discovery-store. Тест: исключение persist → кандидаты доступны следующему discovery. Сложность: S.
3. **A3. Recovery batch 2→10** (QR-5) + клэмп `delaySeconds ≤ 900` (QR-6). Тесты в lead-radar-queue-reliability. Сложность: S.
4. **A4. Discovery dead letter не терминирует running-детей; generation-суффикс replenish-ключа** (QR-7). Сложность: M.
5. **A5. Качество в статусе поиска** (QR-8): в candidate-режиме добавить в summary `contactPotentialCount` (lookup-eligible кандидаты) и не показывать `ready` без пояснения; честный знаменатель (DS-3). Сложность: M (затрагивает summary-контракт + UI).

Критерии этапа: ни одна компания не теряется молча; статус поиска всегда объясняет «сколько сделано / что ждётся / до какого времени».

## Этап B — модель контакта и ownership (выход Telegram)

1. **B1. Ручной tier для каталожных username** (DS-2): resolved-но-unconfirmed контакты получают явный статус «нужна ручная привязка» (не считать в contactTarget автоматически); оператор подтверждает принадлежность → контакт получает `reason='manually_confirmed_corporate'` с отдельным evidence (operator, время) и может входить в строгое множество ТОЛЬКО при активном authorization. Серверный preflight требует этот reason явно. Миграция: колонка/JSON-поле reason уже есть — нужен только разрешённый список значений + UI-действие. Сложность: M. Это главный рычаг yield без ослабления автоматических проверок.
2. **B2. Стабилизация proof-дайджеста** (TG-2): исключить `observedAt` из identity-компонента id источника / сортировать sources перед хешем; при изменении proof — обновлять существующий check вместо инвалидации, если candidate key и endpoint совпали. Тест: повторный enrichment с новым observedAt не снимает verified. Сложность: S-M.
3. **B3. TTL-предвестие** (TG-1): перед prepare кампании пакетно перепроверять истекающие в течение 24 ч контакты (кнопка уже есть — добавить автоматический вызов preflight'ом с показом «обновлено N»). Сложность: S.
4. **B4. Бесплатный discovery-путь для собственного сайта** (DS-1/DS-5): для компаний с сайтом проверять sitemap.xml + эвристику `/contacts|/kontakt|/aloqa` прямым бесплатным fetch ДО Firecrawl (сейчас прямой fetch есть только для главной в enrichment); для no_website — честный terminal status вместо молчаливой парковки. Сложность: M. Уменьшает зависимость от бюджета без расширения поиска (требование ТЗ: не бесконечно расширять).

## Этап C — кампания (безопасность отправки)

1. **C1. CLAIM_LEASE_MS 120с → ≥180с** (CP-1): одна константа + тест «send 125 с не рождает ambiguous». Сложность: XS. **Входит в MVP-гейт.**
2. **C2. Реконсиляция sent/ambiguous** (CP-2): расширить maintain() на пары с существующим providerMessageId. Сложность: S. **MVP-гейт.**
3. **C3. Лимит длины по UTF-16** (CP-4): `.length` вместо code points в двух местах + тест с эмодзи. Сложность: XS.
4. **C4. Персистентный draft текста** (CP-3): sessionStorage для template + сброс при смене выдачи; не блокировать ввод при operationBusy (CP-6). Сложность: S.
5. **C5. Мелкие UX**: CP-5 (сообщение о pending media), CP-6 остатки. Сложность: XS-S.

## Этап D — каталог и UI-согласованность

1. **D1. Лимиты каталога** (TG-3): SQL-пагинация до группировки / кэш строгой верификации на 5-15 мин / индекс по contact_keys. Сложность: M. Без этого рост базы ломает каталог 422-ами.
2. **D2. Единый источник статусов**: endpoint вычисления статусов каталога и карточки поиска на одной функции (уже близко); в UI подписывать TTL верификации («подтверждён до HH:MM»). Сложность: S-M.

## Этап E — сквозная приёмка первой кампании (внешние эффекты — по отдельному разрешению)

1. E1. Живая проверка аккаунта: карточка current session + heartbeat (не vault).
2. E2. Один согласованный live-получатель (из владельца), минимальная кампания на 1 адресата: preflight → approval → send → receipt → отсутствие дубля → Pause/Stop на второй кампании.
3. E3. Фиксация evidence: campaign_effects, bridge ledger, D1-агрегаты. До E1-E3 «первая рассылка проверена» утверждать нельзя.
