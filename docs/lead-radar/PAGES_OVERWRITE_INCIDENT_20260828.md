# Исчезновение Lead Radar после параллельной публикации

## Подтверждённая причина

28 августа 2026 года один production-проект Cloudflare Pages (`ai-direct-pro-landing`, домен `gptbot.uz`) публиковался из двух расходящихся worktree. Pages заменяет весь сайт и конфигурацию, а не только изменённые SEO-страницы.

- 13:58 UTC: выпуск Lead Radar `d629b4b`, deployment `95d31e78-4a9c-4ca0-ba73-bed74059d3c4`.
- 14:02 UTC: SEO-ветка `b2a9cc1`, deployment `7c594bab-4e76-4f89-967e-1c539c6e6f6a`.
- 14:12 UTC: SEO-ветка `9cdfff1`, deployment `1ed19d97-2bde-41e8-b289-dd895daa5589`.

В SEO-ветке был старый интерфейс без общей базы, Bridge и кампаний. Её публикация также заменила `LEAD_RADAR_TELEGRAM_CAMPAIGN_ENABLED` и `LEAD_RADAR_TELEGRAM_CAMPAIGN_AUTOSEND_ENABLED` на `false`. Загружавшийся с домена `AdminRoot-7Y-N1D9_.js` и PDF пользователя соответствуют этой старой версии. Это не потеря базы и не сброс Telegram-сессии.

Read-only аудит: все пять проверок схем проходят, в каталоге сохранены 37 групп, активных работ нет. Количество контактов не означает разрешение на отправку. Во время восстановления не удалялись данные, не создавались согласия, не выполнялись рассылки или платные запросы Firecrawl.

## Исправление

Merge `5311cc1` объединяет последние три SEO-коммита с текущим Lead Radar. Сохраняются RU/UZ-страницы, новые ссылки футера, общая база, мобильные/username, Bridge и серверная проверка готовности. Возвращаются ранее одобренные флаги кампаний; legacy Business API остаётся выключенным, лимит 30/UTC-сутки и интервал 120 секунд не меняются.

Тест parity-конфигурации обновлён с устаревшего снимка 27 августа на одобренный интегрированный выпуск. Проверки оснований, подтверждения аккаунта, запретов и защиты от повторной отправки остаются независимыми серверными условиями.

## Правило следующих публикаций

Публиковать **весь объединённый проект**, не отдельный SEO-worktree с отставшей админкой:

```text
npm run build:production
npm run release:pages:check
npm run deploy:pages:production
```

Ключ Cloudflare передаётся только через окружение. Изменения runtime должны быть проверены и закоммичены до сборки. Локальные AGENTS/заметки не включаются в выпуск.

Новый guard проверяет:

1. Сборка содержит достижимые из `index.html` модули базы контактов, Bridge, readiness и новые API-маршруты. Оставшийся рядом неиспользуемый новый chunk не маскирует старый entry point.
2. RU/UZ SEO-страницы и футер, отдельная админка сохранены.
3. SHA256 всех файлов `dist` и commit совпадают с `gptbot-release.json`.
4. HEAD содержит и последний выпуск Lead Radar, и SEO-исправления, и **текущий** успешный production commit. Неизвестная/неслитая версия блокирует публикацию.
5. Общая для git-worktree блокировка не допускает две одновременные публикации через guard; после загрузки проверяются canonical commit и manifest на домене.

Ограничение: прямой `wrangler pages deploy` или внешняя CI-система может обойти локальный guard. Всем авторам публикаций нужно перейти на эту команду. Guard не меняет права Cloudflare и не останавливает чужие процессы. Потерянную после аварии lock-файл удаляют только после проверки, что публикация завершена.

## Проверки и границы приёмки

Добавлены regression-тесты старой/односторонней ветки, недостижимых chunks, отсутствующих функций/SEO, устаревшего manifest и композиции всей страницы. Полная браузерная fixture `tests/browser-fixtures/lead-radar-page.html` использует вымышленные компании и блокирует любые реальные сетевые вызовы.

В браузере Codex нет авторизованной owner-сессии; рабочие кнопки проверены на полной локальной fixture, production — по версии, файлам, конфигурации и read-only данным. Это не тест реальной отправки.

- Runtime `d2a148ae6acabef63bb8f4f4f2a0b41148f305ac`; Pages production `37b7a90e-32f5-427a-89f2-5c9d78d8a298`, 14:32 UTC, success. Gateway и automation Worker не менялись.
- Guard подтвердил ancestry текущей production-версии перед публикацией, 860 файлов сборки, все шесть feature checks, а после публикации — canonical commit и manifest непосредственно на `gptbot.uz`.
- Live `AdminRoot-MWr7TJlD.js` и API chunk `triangle-alert-DcMMNCfU.js`: HTTP200 и SHA256 совпадают с локальной сборкой. Login HTML загружает новый `index-Bt9kyYaX.js`. RU/UZ рекламные страницы и новые footer-секции HTTP200.
- Production account/campaign/autosend flags `true`, legacy contact `false`, daily30/minInterval120/local_bridge подтверждены Cloudflare API после публикации. Ранее отключённые campaign-флаги восстановлены, а не отключены защитные проверки получателей.
- Повторный read-only audit: все пять schema gates pass, 37 групп каталога и те же source counts, activity[]. Windows Bridge task Running. Миграций, сбросов сессии/ключей, платных запросов и реальных отправок не было.
- Все 40 файлов regression-набора Lead Radar/SEO/config/production-guard/secret-scan прошли. Typecheck, full ESLint, secret scan (3976 файлов), обе production-сборки прошли. Предупреждение о размере admin chunk остаётся; это не ошибка сборки.
- Full-page browser fixture: переход из истории в поиск, Bridge/account/campaign/readiness видны; текст редактируется; общая база выбирает mobile+username одной кнопкой; аудитория 2/2 сохраняется после reload; preflight без основания не разрешает отправку. Тестовые вкладки и Vite закрыты.

После обновления страницы браузер загрузит исправленную админку. Повторная привязка Telegram из-за этого инцидента не требуется. Следующие SEO-публикации должны включать этот объединённый release и использовать guard, иначе raw upload по-прежнему способен заменить весь сайт старой версией.
