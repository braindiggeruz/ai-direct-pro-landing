# ADR — как частный продавец получает право опубликовать объявление

Дата: 2026-08-03 · Статус: **PROPOSED · требует owner gate**
Ветка: `feature/bormi-quickpost` · База: `7fd74fc`
Автор решения по данным: live D1 `gptbot-ai-drafts` (read-only, `rows_written: 0`)

---

## 1. Вопрос

QuickPost обещает: «Сфотографируйте вещь, расскажите о ней, укажите цену — Bormi
подготовит объявление». Обещание невыполнимо, если для публикации нужно уйти в
бот и завести магазин.

Значит нужен ответ: **откуда у обычного человека берётся право опубликовать одну
личную вещь**, и что для этого должно измениться в домене.

Гипотеза, которую поручено проверить первой:

> MODEL A — private seller profile как минимальный server-created container,
> скрытый от пользовательского интерфейса.

---

## 2. Что показала реальная схема (не отчёты)

Прочитано из живой D1, а не из документации.

```
sotuvchi_stores.org_id            UNIQUE  REFERENCES organizations(id)
memberships (org_id, identity_id) UNIQUE  role IN ('owner','staff')
sotuvchi_products                 FK (org_id, store_id) → sotuvchi_stores
sotuvchi_products.category_id     FK (org_id, store_id, category_id)
sotuvchi_categories               UNIQUE (store_id, slug)  — категории живут В магазине
sotuvchi_onboardings.owner_identity_id UNIQUE, .org_id UNIQUE
```

Продуктовая таблица **не имеет** колонок: владелец-идентичность, состояние
товара, локация, тип продавца, контактные предпочтения.

Живое состояние: 1 организация, 1 магазин, 1 membership, 0 onboardings,
48 товаров, 7 категорий, 8 identities. Ledger `d1_migrations` = 25,
последняя запись `0025_owner_control_center_audit.sql`.

### 2.1. Решающий факт: покупатель видит ровно одну витрину

`functions/market/access.ts` связывает сессию покупателя с **одним**
`(org_id, store_id)`:

```
resolveStorefrontRoute(...)  →  { orgId, storeId }
resolveStoredStorefrontContext(...)
resolveDirectPilotStorefront(botUsername)
```

Каталог, поиск и главная читают из `access.buyer.storeId`. Кросс-магазинного
чтения не существует.

**Следствие:** товар, опубликованный в другом магазине, покупателю не виден
вообще. Не «плохо ранжируется» — его нет ни в одном запросе.

## 3. Оценка моделей

### MODEL A — невидимая частная витрина поверх Sotuvchi domain

Механика: сервер идемпотентно создаёт `organization` + `sotuvchi_store` +
`membership(owner)` на identity, затем публикует товар туда.

Схема это допускает: `stores.org_id` UNIQUE не нарушается, потому что
организация тоже новая. Миграция формально не нужна.

**Но модель нежизнеспособна по трём независимым причинам:**

1. **Публикация в пустоту.** Ни одна сессия покупателя не привязана к новой
   витрине. Объявление пройдёт валидацию, вернёт 201 и не появится ни в одном
   покупательском экране. Это хуже текущего bot fallback: сейчас человек хотя бы
   понимает, что его выкинули в бота, а здесь ему скажут «опубликовано».
2. **Фрагментация категорий.** `sotuvchi_categories` живут внутри магазина, а FK
   товара — составной `(org_id, store_id, category_id)`. Каждая частная витрина
   получила бы собственные 7 категорий-дублей, либо `category_id = NULL`.
   Категории перестают быть общим словарём — ломается и поиск, и AI-подсказка
   категории, которая грунтуется на списке категорий витрины.
3. **Рост на пустом месте.** Один частник = 1 organization + 1 store +
   1 membership + N категорий. Тысяча частников — тысяча организаций в таблице,
   которая описывает бизнесы. Модерация, поддержка и любой будущий tenant-отчёт
   получают тысячи фиктивных «компаний».

**Вердикт: ОТКЛОНЕНА.** Предпочтительная гипотеза не подтвердилась. Проверка
схемы была не формальностью — она модель и убила.

### MODEL B — связь listing → identity без organization/store

Механика: у объявления появляется владелец-идентичность, а покупательское
чтение перестаёт быть однолавочным.

Требует минимум:

* колонку владельца на товаре (или таблицу владения);
* колонки `condition`, `location`, `seller_type`, contact preference — либо
  честное решение держать их в `specifications_json`;
* общий словарь категорий вне магазина;
* переписанный buyer read: сегодня он `WHERE store_id = ?`.

Это и есть «one-store shop window → listings board», уже названная в
`0563f54 docs(market): map the road from a one-store shop window to a listings board`.

**Вердикт: ЦЕЛЕВАЯ МОДЕЛЬ, но это миграция и переписанное покупательское чтение.**
Не входит в QuickPost slice и требует отдельного owner gate.

### MODEL C — bot/onboarding остаётся обязательным для частника

Механика: то, что в проде сейчас. `sellerCommands` выдаётся только владельцу
организации; частник уходит по `t.me/BormiMarketBot?start=agent_seller`.

Плюсы: ноль изменений, ноль риска, полная изоляция tenant.
Минусы: ровно тот UX, который поручено убрать.

**Вердикт: ОСТАЁТСЯ ТОЛЬКО КАК FALLBACK**, а не как основной путь.

## 4. Сравнение

| | A · невидимая витрина | B · listing → identity | C · бот обязателен |
| --- | --- | --- | --- |
| Reuse существующего домена | высокий | средний | полный |
| Безопасность / tenant isolation | сохраняется | требует новых проверок | максимальная |
| Migration | не нужна | **нужна** | не нужна |
| Совместимость старого клиента | полная | полная | полная |
| Виден ли товар покупателю | **нет** | да | да |
| Общие категории | ломаются | сохраняются | сохраняются |
| Seller commands | переиспользуются | переиспользуются | переиспользуются |
| Частник vs бизнес | неразличимы | различимы | различимы |
| Модерация | тысячи фиктивных орг. | по владельцу | по магазину |
| Rollback | флаг | флаг + миграция назад | — |
| Support burden | высокий | средний | высокий (UX) |
| UX | ложное «опубликовано» | целевой | выталкивает из Mini App |
| SEO / Bormi Match | нечего индексировать | основа для обоих | как сейчас |

## 5. Решение

1. **QP-1 выпускается без частного провижининга.** QuickPost — композер внутри
   Mini App для тех, у кого `sellerCommands` уже есть. Он не требует ни
   миграции, ни новой authority, ни нового домена: `POST /seller/products` и
   `POST /seller/products/:id/publish` уже существуют.
2. **Частный продавец в QP-1 получает честный fallback**, а не ложную
   публикацию: та же ссылка в бота, но с текстом про объявление, а не про
   «создание магазина».
3. **QP-2 = MODEL B и заблокирован owner gate.** Он начинается не с кода, а с
   reconciliation ledger `0025` против физических `0026–0030`, backup,
   physical introspection, rehearsal и forward/rollback SQL.
4. **MODEL A не реализуется.** Идемпотентная server-команда провижининга не
   пишется, потому что она создавала бы объявления, которых никто не увидит.

`MARKET_PRIVATE_SELLER_PROVISIONING_ENABLED` вводится как объявленный, но
неиспользуемый переключатель только вместе с QP-2 — сейчас он не добавляется,
чтобы не заводить флаг без кода за ним.

---

## 6. Owner gate — что именно требуется решить

Один консолидированный вопрос, до любого кода QP-2:

1. Подтвердить, что Bormi становится **досками объявлений**, а не витриной
   одного магазина — то есть покупательское чтение перестаёт быть `store_id = ?`.
2. Разрешить работу с migration ledger: сверку `0025` против физических
   `0026–0030`, backup и rehearsal на копии.
3. Разрешить миграцию, добавляющую владение объявлением и общий словарь
   категорий, с точным blast radius (48 существующих товаров, 1 магазин).
4. Решить, где живут `condition` и `location`: колонки или зарезервированные
   ключи в `specifications_json`.

До ответа: `PRIVATE_SELLER_PROVISIONING = BLOCKED`.

---

## 7. Что этот ADR НЕ разрешает

Создание organizations/stores/memberships из Mini App; выдачу authority
клиентом; параллельный marketplace backend для частников; remote migration;
изменение `sotuvchi_stores.org_id`; фиктивный onboarding; публикацию в витрину,
к которой не привязана ни одна покупательская сессия.
