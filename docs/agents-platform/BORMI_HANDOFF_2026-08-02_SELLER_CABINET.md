# 3. Что было до сессии — фактический аудит

Прочитан реальный код, не отчёты.

## 3.1. Backend продавца был готов на ~70 %

`functions/market/router.ts` уже отдавал 9 GET-эндпоинтов и 8 команд с
`expectedVersion`, `Idempotency-Key` и rate limit. Кабинет — это фронт поверх
существующего, а не второй маркетплейс.

## 3.2. Четыре находки, определившие план

1. **Фото добавить было нельзя в принципе.** `mediaRefs` — это Telegram
   `file_id`, отдаётся через `proxyTelegramMedia` с `private, noindex`. В Mini
   App не было ни одного элемента загрузки, R2 в market-контуре не использовался.

2. **`searchTerms` и `specifications` — мёртвый капитал.** Добавлены миграцией
   `0027_market_catalog_quality.sql`, участвуют в `rankCatalogProducts`, но
   заполнить их из интерфейса было невозможно. У всех товаров пусто.

3. **Заказов видно максимум 5.** Тройной потолок: `Math.min(5, ...)` в роутере,
   `Math.min(requireSellerLimit(rawLimit, 5), 5)` в сервисе и
   `SELLER_ORDER_LIMITS.listLimit = 10` в валидаторе. Пагинации не было нигде —
   `nextCursor` всегда `null`.

4. **AI-фасад не умеет vision.** `functions/platform/ai/` имеет `complete`,
   `structured`, `transcribe`. `AiMessage.content` — это `string`. Картинку
   послать нечем.

## 3.3. Прочие дефекты, найденные и учтённые

- дашборд был vanity (3 счётчика + 2 списка), а не exception-first;
- настроек магазина нет ни на сервере, ни в UI;
- статистика только за сутки — `STATS_WINDOW_DAYS = 1`, 7д/30д бэкенд не отдаёт;
- цена вводилась голым `type="number"`, опечатка в разряде ничем не ловилась;
- конфликт версий показывался голой строкой без пути восстановления;
- публичного каталога товаров в вебе нет — только лендинги `/ru/sotuvchi/`.

# 4. Что построено

## 4.1. Фаза 1 — фундамент кабинета

### Сервер

| Изменение | Файл |
|---|---|
| Потолок очереди заказов 5 → 50 | `agents/sotuvchi/orders/validation.ts` |
| Keyset-пагинация `listOrderPage` | `agents/sotuvchi/orders/service.ts` |
| Фильтр по статусу в SQL | `agents/sotuvchi/orders/store.ts` |
| Курсор как непрозрачная строка | `agents/sotuvchi/orders/validation.ts` |
| Лимит листинга каталога владельца до 100 | `agents/sotuvchi/catalog/validation.ts` |
| `GET /seller/overview` | `market/router.ts` |

**Как устроена пагинация.** Очередь отсортирована `placed_at DESC, id ASC`,
поэтому граница страницы требует обе половины ключа. Страница читается на одну
строку глубже запрошенного: лишняя строка не возвращается, она только отвечает
на вопрос «есть ли следующая». Иначе `nextCursor` был бы догадкой по короткой
странице.

**Почему фильтр по статусу сложнее, чем кажется.** Seller-статус выводится из
пары `status` + `fulfillment_status`:

```text
placed     = ('placed',    'none')
confirmed  = ('placed',    'confirmed')
done       = ('placed',    'done')
cancelled  = ('cancelled', 'none')
```

Фильтр по одному `status = 'placed'` подмешал бы подтверждённые заказы в
очередь новых. В `store.ts` добавлена карта `STORED_STATUS`, фильтр читает обе
колонки.

**Курсор.** Base64url от `{p: placedAt, i: orderId}`. Внутри нет магазина, нет
личности, нет арифметики смещения. Валидация строгая: ISO-таймстамп по regexp
плюс `Date.parse`, id через `requireSellerId`, посторонние ключи в объекте
отвергаются.

**`/seller/overview` — exception-first.** Собирается из тех же сервисов, что
читают детальные экраны, поэтому не может заявить работу, которой нет в очереди
за ним. Шесть групп в порядке срочности:

```text
newOrders      статус placed, с возрастом в минутах
agingOrders    confirmed старше SLA (24 ч)
openQuestions  handoffs со статусом open
outOfStock     опубликованные товары с onHand = 0
drafts         черновики
weakProducts   опубликованные без фото / описания / характеристик / поисковых слов
```

Каждая группа сообщает `truncated` — упёрлось ли чтение в глубину скана.
Считается по **источнику**, не по отфильтрованному результату: группа может быть
короткой после фильтра и всё равно неполной. Иначе частичное чтение читалось бы
как «это всё».

### Клиент

`apps/market-mini-app/src/screens/SellerApp.tsx` переписан целиком (19 KB → ~50 KB).

Навигация: **Сегодня · Заказы · Товары · Вопросы · Остатки**.

- «Сегодня»: только то, что требует действия. Пустые группы не рендерятся.
  Всё чисто — «Всё разобрано» и кнопка добавить товар.
- Заказы: сегменты Все/Новые/Подтверждён/Выполнен/Отменён, `useInfiniteQuery`
  по курсору, «Показать ещё». В детали добавлен предпросмотр остатка после
  подтверждения (`8 → 6`).
- Товары: сегменты по статусу, поиск по названию, значок «Слабая карточка».
- Конфликт версий: компонент `ConflictNotice` сам перечитывает запись и
  сохраняет введённое. Подключён ко всем пяти мутациям с версией — заказ, ответ
  на вопрос, сохранение товара, публикация, остаток.

## 4.2. Фаза 3 — редактор товара v2

- **Характеристики**: строки RU-метка / UZ-метка / значение. Машинный ключ
  генерируется транслитерацией русской метки под доменный паттерн
  `[a-z][a-z0-9_]{0,31}`, поэтому два товара с «Цвет» попадают на один ключ.
  Существующие строки сохраняют свой ключ.
- **Поисковые слова**: чипы, до 12, добавление по Enter/запятой.
- **Цена**: живое форматирование под полем — `349 000 сум · Проверьте разряды`.
- **Предпросмотр** карточки глазами покупателя.

Серверных изменений не потребовалось: `normalizeCreateProductInput` и
`normalizeUpdateProductInput` уже валидировали оба поля. Нужно было только
довезти их до DTO и до формы.

**Owner-блок в DTO.** `productDto(...)` получил седьмой параметр `owner`.
Только на `/seller/*` в ответ добавляется:

```ts
owner: {
  mediaRefs: string[];                                   // сырые ссылки
  searchTerms: string[];                                 // алиасы продавца
  specifications: { key, labelRu, labelUz, value }[];    // обе метки
}
```

Покупательская карточка их не получает — иначе ключевые слова одного магазина
уехали бы любому, кто открыл каталог.

## 4.3. Фаза 2 — фото из кабинета

### Ключевое решение: миграция не нужна

Валидатор медиа в каталоге:

```ts
const SAFE_MEDIA_REF = /^[A-Za-z0-9][A-Za-z0-9._:-]*$/;
```

Точка разрешена. Telegram `file_id` — base64url, точек не содержит. Значит
ссылка `r2.<16 символов base32>` однозначно отличима от телеграмной и ложится в
уже существующую колонку `media_refs_json`.

**Следствие:** расхождение леджера миграций `0025` против физических
`0026–0030` осталось нетронутым и ничего не заблокировало. Ни новой таблицы, ни
`ALTER`, ни одной записи в схему.

### Конвейер

```text
фото (клиент)
  → compressImage(): canvas, длинная сторона ≤1600 px, JPEG q=0.82
  → POST /seller/media, сырое тело
      requireSellerCommands + Idempotency-Key + rate limit 'command'
      readImageUpload(): sniff магических байтов, двойная проверка размера
      R2 put: market/{orgId}/{storeId}/{id}
      → { ref: "r2.<id>", contentType }
  → продавец сохраняет товар
  → PATCH /seller/products/{id} с mediaRefs
```

### Правила безопасности, реализованные явно

- **Тип берётся из байтов, не из заголовка.** Объявленный `Content-Type`
  принимается, только если сигнатура с ним согласна. HTML, переименованный в
  `.jpg`, иначе был бы сохранён и отдан обратно как картинка — это stored-XSS.
- **Размер ограничен дважды**: по `Content-Length` до чтения и по фактическим
  байтам после. Отсутствующий или лживый заголовок не превращается в
  безлимитное чтение. Потолок 5 MB.
- **Ключ несёт org и store.** Авторитет выражен самим путём: хендл, разрешённый
  в одном магазине, не соберёт ключ в чужом префиксе. `mediaObjectKey`
  возвращает `null` на любых id с `/`, пробелами, пустых.
- **Отдача** повторяет заголовки телеграмного прокси: `private, max-age=300`,
  `X-Robots-Tag: noindex, nofollow`, `Content-Security-Policy: default-src 'none'; sandbox`,
  `X-Content-Type-Options: nosniff`. Недоказанный тип деградирует в
  `application/octet-stream`. Публичного URL у бакета нет.
- **Отказ закрытый по двум условиям**: флаг `MARKET_SELLER_MEDIA_UPLOAD_ENABLED`
  строго `"true"` **и** биндинг `MARKET_MEDIA` существует. Иначе 503, а кабинет
  прячет пикер — та же дисциплина, что у микрофона.

### Клиент

- Пикер `<input type="file" accept="image/jpeg,image/png,image/webp" multiple>`,
  визуально скрытый, обёрнут в `<label>`.
- Загрузка последовательная, не параллельная: на мобильном канале продавец
  получает первое фото раньше, а ошибка называет конкретный файл.
- До 5 фото. Первое — обложка, есть действие «сделать обложкой»; свободного
  перетаскивания нет намеренно — оно конфликтует с жестами Telegram-шторки.
- Снятие фото до сохранения вызывает `DELETE /seller/media/{ref}` и отзывает
  object URL.

# 7. Тесты

## 7.1. Новый файл

`tests/market-seller-cabinet.test.ts` — 20 тестов, 573 строки.

**Рантайм через SQLite-D1 (реальные сервисы, не моки):**

- очередь больше не режется на пятом заказе; старый массивный ридер сохраняет
  свой дефолт 5 — бот-поток не тронут;
- лимит выше доменного потолка отвергается, нулевой тоже;
- пагинация не повторяет и не пропускает ни одного заказа, сходится по guard;
- курсор непрозрачен, шесть форм подделки отвергаются, включая `../other` в id
  и лишний ключ в объекте;
- фильтр по статусу читает пару колонок, а не производное имя;
- один магазин не пролезает курсором в очередь другого.

**Загрузка фото:**

- sniff распознаёт JPEG/PNG/WEBP, отвергает HTML и GIF;
- PNG, объявленный как JPEG, отвергается;
- размер сверх потолка отвергается по факту, а не по заявленному заголовку;
- ключ всегда несёт org и store; traversal и инъекции в id дают `null`;
- телеграмная ссылка не считается хранимой и не строит ключ;
- 500 сгенерированных ссылок без единого повтора;
- отдача private/noindex/sandbox/nosniff, недоказанный тип деградирует;
- **ссылка `r2.<id>` реально проходит боевой regexp каталога** — regexp
  вытаскивается из исходника и применяется, а не переписывается в тесте.

**Контрактные (по исходникам):**

- домашний экран собран из тех же сервисов, что детальные;
- `truncated` считается от глубины скана;
- owner-поля не уезжают на покупательскую карточку (проверяется число
  owner-флагов в вызовах DTO);
- у всех пяти мутаций есть восстановление после 409;
- редактор дотягивается до всех ранжируемых полей;

## Фаза 4 — AI-студия (6 д)

**Единственный технический блокер: в платформенном AI-контракте нет vision.**

Нужно:

1. `AiTask` += `'vision'`;
2. `AiMessage.content` расширить до `string | AiContentPart[]`, где part это
   `{type:'text'}` или `{type:'image', mediaType, data}`. **Обратная
   совместимость обязательна** — все существующие вызовы со `string` должны
   продолжать работать без правок;
3. `AiUnavailableError(..., 'vision')` по образцу `'transcribe'`;
4. драйвер с vision-моделью;
5. `POST /seller/drafts/from-media` — возвращает **предложение, не запись**;
6. `POST /seller/drafts/from-voice` — переиспользует уже задеплоенную цепочку
   Groq Whisper → OpenAI и существующий `parseBudget`.

**Жёсткое ограничение роли AI**, переносится из голосового поиска без
ослаблений: модель может предложить название, описание, характеристики,
категорию, поисковые слова, alt-текст. Она **не может** назначить цену, остаток,
статус, опубликовать товар. Этих полей не должно быть в схеме ответа физически,
а не по договорённости.

Грунтовка: в prompt подавать существующие категории магазина и
`CatalogVocabularyEntry`, чтобы модель говорила языком этого каталога, а не
выдумывала новые категории.
