# 1. Executive product verdict

**Bormi сегодня — это не маркетплейс и не доска объявлений. Это витрина одного магазина.**

Это не оценка качества, это факт из кода. Покупательский поиск выполняется запросом

```sql
WHERE product.org_id = ? AND product.store_id = ?
  AND product.status = 'published'
JOIN owner_pilot_stores AS pilot ON ... AND pilot.state = 'active'
```

(`functions/agents/sotuvchi/catalog/store.ts:1154`). Один покупатель видит ровно один магазин.
В production сейчас: **1 магазин, 1 активная pilot-строка, 48 товаров, 1 заказ, 1 вопрос**.

Из этого следует главный вывод роадмапа:

> Переход к OLX-подобной модели — это **не переименование «Товар» → «Объявление»**.
> Это введение первого в истории проекта **межмагазинного чтения каталога**
> и первого способа для частного лица стать поставщиком контента.
> Всё остальное (карточки, избранное, контакт-первый CTA) — надстройка над этим решением.

**Что при этом хорошо:** доменное ядро (каталог, поиск, ранжирование, заказы, остатки, вопросы,
уведомления, идемпотентность, версии, media, voice) — рабочее и переиспользуемое почти целиком.
Оценка реального переиспользования для classifieds-модели: **~70 % backend, ~85 % инфраструктуры,
~40 % buyer UI**.

**Что при этом критично:** обнаружена доказанная причина, по которой владелец «не видит изменений»
кабинета продавца. Она не в кеше и не во фронтенде. См. §2.4.

## 2.4. Seller cabinet visibility — ПРИЧИНА НАЙДЕНА

```text
SELLER_CABINET_VISIBLE_TO_OWNER = PROVEN_INVISIBLE
```

Это сильнее, чем `NOT_PROVEN`. Доказательство цепочкой из кода и данных:

1. `App.tsx:39` — переключатель «Покупатель / Продавец» рендерится только при
   `bootstrap.data.flags.sellerRead === true`.
2. `functions/market/access.ts:162-181` — `sellerOrg` выдаётся **только** если
   `onboarding?.status === 'completed' && onboarding.store?.status === 'active'`.
3. `onboarding/service.ts:310-323` — `getOnboarding` читает **исключительно** запись из
   `sotuvchi_onboardings` по `owner_identity_id`. Fallback на membership отсутствует.
4. D1 production: `SELECT COUNT(*) FROM sotuvchi_onboardings` → **0**.
5. D1 production: единственная строка `memberships` (role=owner) принадлежит identity с
   `provider = 'api'`. Все **4 Telegram-личности не имеют ни одного membership**.

**Вывод:** магазин был создан не через onboarding-workflow, а напрямую (seed/скрипт). Поэтому
`flags.sellerRead` равен `false` для **любого** пользователя Telegram, включая владельца.
Кабинет продавца физически недостижим — не из-за кеша, не из-за бандла, не из-за UI.

Service worker v7 был нужен, но к этому симптому отношения не имеет. Пункт 11 предыдущего handoff
закрывается: причина — данные и модель авторитета, а не фронтенд.

**Что это НЕ означает:** это не баг безопасности. Система fail-closed отработала правильно: она
отказала в правах, потому что доказательства владения магазином в базе нет.

**Что требуется для устранения (owner gate, не выполнено):** запись в `sotuvchi_onboardings` +
`memberships` для Telegram-личности владельца, либо расширение `resolveMarketAccess` на путь
«membership owner + активный store» как альтернативный источник авторитета. Первое — данные,
второе — код. Оба требуют отдельного разрешения (§46, гейт G-05).

## 4.2. Пять структурных конфликтов

**К-1. Единственный магазин.** Покупательский контекст — это `StorefrontContext { orgId, storeId }`.
Поиск, категории, сравнение, checkout — всё привязано к одному store. Доска объявлений требует
чтения поверх всех магазинов. Это самый дорогой конфликт.

**К-2. Товар ≠ объявление.** `CatalogProduct` (`catalog/types.ts:41`) содержит: id, orgId, storeId,
categoryId, sku, name, description, priceMinor, currency, availability, status, mediaRefs,
searchTerms, specifications, version, timestamps. В нём **нет**: локации, состояния (новое/б/у),
типа объявления, срока годности, контакта, признака «торг уместен», признака частный/бизнес.

**К-3. Заказ ≠ отклик.** Checkout — это шестишаговая транзакция с количеством, именем, телефоном и
адресом покупателя. Отклик на объявление — это сообщение. Разная стоимость входа: заявка требует
шести шагов, отклик — одного.

**К-4. Продавец = организация.** `sotuvchi_stores.org_id` объявлен `UNIQUE`. Одна организация — один
магазин. Частное лицо, публикующее один диван, вынуждено стать организацией. Это работоспособно
(и это самый дешёвый путь переиспользования), но требует авто-провижининга.

**К-5. Остаток обязателен.** `sotuvchi_inventory` держит 44 строки на 48 товаров, exception-first
экран считает `onHand = 0` проблемой. Для частного объявления остатка не существует — «продано»
это статус, а не число.

# 5. Продуктовые архетипы (не список конкурентов)

| Архетип | Механика | Что делает ценность | Где ломается |
|---|---|---|---|
| **Каталог-витрина** (текущий Bormi) | продавец ведёт карточки, покупатель ищет и заказывает | точность данных, наличие | требует дисциплины продавца; не масштабируется на частников |
| **Открытая доска** (OLX-архетип) | любой публикует, поиск + фильтры, контакт напрямую | объём предложения | мёртвые объявления, спам, ноль ценности при пустом каталоге |
| **Лента спроса** (архетип «Ищу») | покупатель публикует потребность, продавцы отвечают | работает **при нулевом предложении** | нужен ответ продавца; риск спама к покупателю |
| **Соц-локальный обмен** (Facebook Marketplace) | идентичность из соцграфа, локальность | доверие «из коробки» | у нас нет соцграфа кроме Telegram |
| **Вертикальный агрегатор** | одна категория, глубокие атрибуты | качество match | не подходит к «всё для всех» |
| **Мессенджер-первый рынок** (Telegram-каналы) | сделка в переписке, поиск вручную | нулевой порог входа, привычно | нет структуры, нет поиска, нет истории |

**Позиционирование Bormi:** пересечение «лента спроса» × «мессенджер-первый рынок», с каталогом-
витриной как премиальным слоем для магазинов. Это единственный из шести архетипов, который даёт
ценность в первый день при 48 товарах.

# 6. Концепции killer feature (шесть, не четыре)

## KF-1 — Bormi Match / «Ищу — найдётся» (гипотеза владельца)

Покупатель говорит или пишет, что нужно. Bormi ищет **только реальные опубликованные объявления**.
Если совпадений нет или они слабые — предлагает создать структурированный запрос «Ищу», показывает
предпросмотр, публикует **только после подтверждения человеком**. Релевантные продавцы получают
privacy-safe сигнал спроса (категория + бюджет + район, без личности и без сырой фразы). Продавец
отвечает существующим объявлением или создаёт новое. Покупатель получает уведомление о реальном
совпадении через уже работающий Telegram-бот.

## KF-2 — AI Listing Studio / «Сфотографировал или рассказал — получил черновик»

Продавец снимает фото или наговаривает голосом. Модель предлагает: категорию, заголовок, описание,
характеристики, поисковые слова, alt-текст. **Не предлагает**: цену, остаток, район, контакт,
статус публикации. Публикация — только человеком.

## KF-3 — «Bor / Yo'q» — живой статус объявления

Каждое объявление имеет отметку свежести. Одно нажатие «Ещё есть» продлевает её. Устаревшие
объявления визуально тускнеют, падают в ранжировании и через N дней уходят в архив. Покупатель
видит «подтверждено 2 часа назад» вместо «размещено 4 месяца назад».

## KF-4 — «Рядом» — гиперлокальность до махалли

Лента и фильтр по району/махалле, а не по городу. Сортировка по близости для самовывоза.

## KF-5 — Голосовой торг / ценовой сигнал

По реальным опубликованным объявлениям той же категории показывать «ниже рынка / по рынку / выше».

## KF-6 — Лестница доверия: частник и магазин в одной ленте

Один поток, но визуально разделённые уровни: аноним → подтверждённый телефон → verified магазин с
историей заказов. Магазин получает возможность заказа, частник — только контакт.

# 8. Выбранная killer feature

**Bormi Match — «Ищу — найдётся».**

Почему именно она создаёт новый продуктовый цикл, а не AI-декор:

1. **Она превращает провал в актив.** Сегодня пустая выдача — тупик (`StateView noProducts`).
   В новой модели пустая выдача становится записью спроса. Каждый неудачный поиск делает продукт
   ценнее, а не беднее.
2. **Она создаёт причину вернуться, которой у доски объявлений нет.** OLX не пишет вам, когда
   появился нужный товар. Bormi может — через уже работающего Telegram-бота, без push-инфраструктуры.
3. **Она даёт продавцу то, чего нет нигде:** проверяемый спрос до вложений. «Три человека за неделю
   искали детскую коляску до 2 млн в вашем районе».
4. **AI в ней вспомогательный.** Он понимает речь и нормализует формулировку. Он не изобретает товар,
   не назначает цену, не публикует. Если убрать AI, механика продолжает работать через текст —
   это признак настоящей продуктовой механики, а не обёртки над моделью.
5. **Она уже на 70 % существует в backend:** `runCatalogSearch`, `interpretVoiceTranscript`,
   `parseBudget`, `handoff` (доставка + TTL + владение + однократность), notification dispatcher,
   идемпотентность.

# 9. Supporting feature

**AI Listing Studio (KF-2) — «Сфотографировал или рассказал — получил черновик».**

Она выбрана supporting, а не killer, по одной причине: она **ответ на сигнал**, а не источник
сигнала. Продавец, получивший «вас ищут», должен опубликовать объявление за 40 секунд, а не за
6 минут ручного заполнения. Studio существует, чтобы Match не упирался в трение публикации.

**Прицепом, почти бесплатно:** KF-3 «Bor / Yo'q» встраивается в карточку объявления как trust-
примитив (§31) — не как отдельная фича, а как поле свежести и одна кнопка продления. Стоимость
близка к нулю, потому что `availability` и `updatedAt` уже есть.

# 14. Demand-side journey (целевой)

```text
Открыл Bormi
  → «Что ищете сегодня?» (текст или микрофон)
  → Bormi понимает: предмет, бюджет, район, состояние
  → ЕСТЬ СОВПАДЕНИЯ
        → карточки: фото, цена, район, «подтверждено N часов назад», тип продавца
        → карточка → [Написать] [Позвонить] [В избранное]
        → диалог (handoff-канал) → сделка вне платформы
  → НЕТ СОВПАДЕНИЙ (честно: «Сейчас такого нет»)
        → «Хотите, спросим у продавцов?»
        → предпросмотр запроса «Ищу»: предмет · бюджет · район · состояние · срок
        → пользователь правит и подтверждает          ← публикация только здесь
        → запрос опубликован, ему присвоен TTL
        → релевантные продавцы получают сигнал (без личности покупателя)
        → продавец отвечает объявлением
        → покупатель получает уведомление от @BormiMarketBot
        → возврат в Mini App → диалог
```

Ключевые честности: система никогда не говорит «нашли», если совпадения нет; никогда не публикует
без подтверждения; никогда не показывает продавцу сырой текст запроса.

# 17. Варианты нижней навигации

## N1 — гипотеза владельца

`Главная · Поиск · Подать · Избранное · Кабинет`

- **За:** «Подать» в центре решает главную проблему — дефицит предложения; Избранное — дешёвый
  драйвер возврата; Кабинет — одна дверь ко всему личному; ровно 5 элементов (лимит правила
  `bottom-nav-limit`).
- **Против:** сообщения не на первом уровне — отклик может быть замечен поздно.
- **Смягчение:** уведомления доставляет @BormiMarketBot нативно, badge на «Кабинет» показывает
  непрочитанное.

## N2 — messaging-first

`Поиск · Ищу · Подать · Сообщения · Кабинет`

- **За:** оба конца двустороннего цикла на первом уровне; «Ищу» получает витрину.
- **Против:** нет «Главной» — при пустом каталоге поиск как первый экран показывает ничто; два таба
  («Ищу» и «Сообщения») при малом трафике будут пустыми, а пустой таб выглядит как сломанный продукт;
  «Ищу» непонятно новичку без объяснения.

## N3 — минимальная

`Главная · Поиск · Подать · Кабинет` (4 таба, избранное внутри кабинета)

- **За:** самое дешёвое изменение, сетка `repeat(4, 1fr)` не меняется; меньше пустых поверхностей.
- **Против:** избранное спрятано на два тапа — теряется главный дешёвый механизм возврата.

| Скорость ответа на отклик | 3 | 5 | 3 |
| Устойчивость к пустому каталогу | 4 | 2 | 4 |

# 18. Финальная рекомендуемая navigation

**N1.** N3 набирает формально больше только за счёт дешевизны, но выигрыш в стоимости
одноразовый, а потеря возвращаемости — постоянная.

```text
[ Главная ] [ Поиск ] [ ➕ Подать ] [ Избранное ] [ Кабинет ]
```

Инженерные требования:

- `grid-template-columns: repeat(4, 1fr)` → `repeat(5, 1fr)` в `.bottom-nav` (`styles.css:192`);
  на 320 px ячейка 64 px — сохраняет цель ≥44 px, но требует повторной проверки в 200 % zoom;
- «Подать» — заметная, но не агрессивная: акцент `--action-primary` (`#5b3cf2`), увеличенная иконка,
  **без** плавающего FAB (конфликт с compare-tray и с жестами шторки Telegram — то же основание, по
  которому FAB был отклонён в голосовом релизе);
- «Сравнение» уходит из нижней навигации; compare-tray сохраняется, но появляется только внутри
  результатов поиска и только когда в выдаче есть orderable-позиции;
- бейдж непрочитанного на «Кабинет» использует существующий `.bottom-nav__icon small`
  (цвет `--bormi-coral`).

# 19. Universal personal cabinet architecture

**Принцип: кабинет один. Роль меняет содержимое, а не приложение.**

```text
GET /me           → { capabilities: { buyer, sellerRead, sellerCommands } }
GET /bootstrap    → { flags, counters, navigation, sellerNavigation }
```

Правило рендера:

```text
Кабинет = [общие разделы всегда]
        + [раздел «Магазин»  ⟸  ТОЛЬКО если flags.sellerRead === true]
```

Что запрещено (и подтверждено кодом как уже соблюдаемое):

- нет выдачи прав через route: `/seller/*` требует `access.sellerOrg` на сервере
  (`router.ts:769-772`);
- нет выдачи прав через query parameter;
- нет выдачи прав через localStorage: сессия memory-only;
- нет выдачи прав через переключатель режима: `App.tsx:40` уже понижает `activeRole` до `buyer`,
  если `sellerAvailable` ложно — этот инвариант обязан сохраниться при переносе в кабинет;
- Owner Control Center остаётся отдельным защищённым инструментом.

Отдельный переключатель «Покупатель / Продавец» в шапке **упраздняется как единственный способ**
обнаружить seller tools. Он может остаться как быстрый переход, но точка истины — раздел «Магазин»
внутри кабинета.

**Прямое следствие для §2.4:** даже после переноса кабинет останется невидимым, пока
`flags.sellerRead` ложен. Перенос устраняет проблему обнаружения, но не проблему авторитета.
Обе нужно закрывать отдельно.

# 24. Listing / contact / order capability model

**Правило: способности вычисляет сервер. Клиент только рисует то, что пришло.**

```ts
// Presenter-level, не колонка в базе на первом этапе.
capabilities: {
  canContact:  boolean;  // есть канал связи (handoff/бот)
  canCall:     boolean;  // продавец разрешил показ телефона
  canOrder:    boolean;  // orderable: магазин + остаток + активный checkout-контур
  canCompare:  boolean;  // только orderable
  canRespond:  boolean;  // для WANTED: продавец может ответить объявлением
}
```

| Тип | Первичный CTA | Вторичный | Checkout | Остаток | Сравнение |
|---|---|---|---|---|---|
| `CLASSIFIED_LISTING` | **Написать** | Позвонить · В избранное | нет | нет | нет |
| `ORDERABLE_CATALOG_ITEM` | **Оформить запрос** | Написать · В избранное | да (существующий) | да | да |
| `WANTED_REQUEST` | **Ответить объявлением** | — | нет | нет | нет |

Переходное правило вывода типа (без миграции): объявление считается `ORDERABLE_CATALOG_ITEM`, если
магазин присутствует в `owner_pilot_stores` со `state='active'`, есть строка `sotuvchi_inventory` и
включён `MARKET_MINI_APP_BUYER_ENABLED`. Иначе — `CLASSIFIED_LISTING`. Это сохраняет текущие
48 товаров ровно в их нынешнем поведении и не ломает ни одного заказа.

# 25. Migration and compatibility strategy

## 25.1. Семь принципов

1. Backend остаётся сердцем: новый classifieds backend рядом не строится.
2. Mini App остаётся лицом.
3. Новая сущность вводится **presenter-first**: сначала `listingDto` поверх `productDto`, потом —
   при доказанной необходимости — собственные таблицы.
4. Внутренние идентификаторы не переименовываются массово (`sotuvchi_*`, `product`, `store` остаются).
5. Каждый этап за флагом и с cohort-разделением buyer/seller.
6. Legacy checkout не удаляется до доказательства новой модели.
7. Ни один существующий order или inventory record не теряется.

## 25.2. Транзитивная архитектура

```text
  Клиент                      Presenter                 Домен (не меняется)
  ────────                    ──────────                ───────────────────
  ListingCard      ←──   listingDto(product, caps)  ←──  CatalogProduct
  ContactBar       ←──   capabilities                ←──  store + inventory + flags
  CheckoutFlow     ←──   productDto (как сейчас)     ←──  checkout service
  WantedCard       ←──   wantedDto                   ←──  (фаза 4: handoff или новая таблица)
```

**Dual-read.** На переходном этапе `GET /catalog/products` продолжает отдавать текущую форму, а
`listingDto` добавляет поля **аддитивно** (`capabilities`, `listingKind`, `freshness`, `area`).
Старый клиент игнорирует лишние ключи; новый использует. Ни одного удалённого поля.

**Compatibility adapter.** Поля объявления, которых нет в схеме, на переходном этапе живут в
`specifications` с зарезервированными ключами (`bormi_area`, `bormi_condition`, `bormi_deal_type`).
Это работает, потому что `specifications` уже валидируется, ранжируется и редактируется.

> **Честное ограничение.** Этот приём был правильным для фото (`r2.<id>` прошёл в существующий
> regexp). Для целого доменного слоя он приемлем только как временная мера **на фазы 2–3**.
> Держать «Ищу», избранное и сообщения в `specifications` и `handoffs` нельзя.
> Поэтому ремонт `d1_migrations` (R-02) — не техдолг, а **предусловие фазы 4**.

## 25.3. Порядок, при котором ничего не ломается

```text
1. Кабинет-оболочка (0 изменений API)
2. Presenter listingDto (аддитивно, 0 миграций)
3. Межмагазинное чтение за флагом, старый путь по умолчанию
4. Ремонт ledger  ← owner gate
5. Настоящие таблицы: listings-расширение, favorites, saved_searches, wanted, reports, blocks
6. Match поверх настоящих таблиц
7. Studio (требует vision в AI-фасаде)
8. Публичные страницы и SEO
```

# 27. Messaging and response flow

**Фундамент — существующий handoff:** TTL, владение, `contentCleared`, ровно одна доставка,
`expectedVersion` на ответе, bot fallback. Это уже реализовано и протестировано.

```text
Покупатель → [Написать] на объявлении
  → POST /handoffs { reason: 'buyer_requested_human', question }
  → продавец видит в «Кабинет → Сообщения» и получает уведомление ботом
  → POST /seller/handoffs/{id}/reply { expectedVersion, reply }
  → покупатель получает ответ ботом и в кабинете
```

Что нужно достроить:

- многосообщенческий диалог (сейчас один вопрос — один ответ);
- список диалогов с непрочитанными;
- блокировка и жалоба прямо из диалога;
- ограничение: продавец не видит контакт покупателя, пока покупатель сам его не передал.

Что **нельзя** делать: аналитику по содержимому сообщений, логирование текста, хранение переписки
дольше объявленного срока.

# 28. Favorites and saved-search flow

```text
♡ на карточке → POST /favorites (идемпотентно) → оптимистично закрашивается
Кабинет/Избранное → GET /favorites → карточки + метка «цена изменилась» / «снято»
Поиск с фильтрами → [Сохранить поиск] → POST /saved-searches { query, filters, notify }
Новое объявление совпало → уведомление ботом → deep link в результаты
```

Правило честности: «цена изменилась» показывается только при фактическом изменении `priceMinor`
относительно сохранённого снимка. Никаких выдуманных «скидка!».

# 29. Wanted-request flow

```text
Пустой результат
  → «Сейчас такого нет» (честный ноль, без имитации поиска)
  → [Попросить у продавцов]
  → черновик запроса: предмет · бюджет · район · состояние · срок действия
      (предмет и бюджет предзаполняются из уже разобранного голоса/текста)
  → ПРЕДПРОСМОТР: «так это увидят продавцы»
  → [Опубликовать]                       ← единственная точка публикации
  → запрос активен N дней, виден в «Кабинет → Мои Ищу»
  → релевантные продавцы получают demandSignalDto:
        категория · диапазон бюджета · район · давность
        БЕЗ имени, телефона, Telegram ID и сырой фразы
  → продавец: [Ответить объявлением] → выбор существующего или создание нового
  → покупателю уведомление: «Нашлось по вашему запросу»
  → [Закрыть запрос] когда нашёл
```

Anti-abuse: лимит активных запросов на пользователя, rate limit на публикацию, автозакрытие по TTL,
запрет контактных данных в тексте запроса (валидация).

# 30. AI boundaries

**Может:**

- распознать речь (Groq Whisper → OpenAI fallback, уже в проде);
- нормализовать формулировку до слов, которые есть в каталоге (`groundQueryInCatalog`);
- предложить категорию из существующих категорий магазина;
- предложить заголовок, описание, характеристики, поисковые слова, alt-текст;
- подготовить черновик запроса «Ищу».

**Не может — физически, а не по договорённости:**

- придумать товар, продавца, наличие;
- назначить цену, остаток, район, статус;
- опубликовать объявление или запрос;
- отправить отклик без подтверждения;
- раскрыть сырой текст запроса покупателя продавцу;
- утверждать, что товар найден, если его нет в выдаче каталога.

**Механизм принуждения:** этих полей не должно быть в схеме структурированного ответа модели.
Прецедент уже есть: голосовой поиск возвращает только `productQuery`, `maxPriceMinor`,
`availability`, `category` — цену товара модель назначить не может, потому что такого поля в
контракте нет. Тот же принцип переносится на Studio и Match.

**Disclosure:** любой сгенерированный текст помечается («Черновик подготовлен автоматически»),
как уже сделано для транскрипта («Распознано автоматически»).

# 31. Moderation and trust model

| Область | Решение |
|---|---|
| Состояния модерации | `draft → pending → published → paused → archived → removed` |
| Автопроверка при публикации | запрещённые категории, контакты в тексте, дубликаты, подозрительная цена |
| Дубликаты | нормализованное имя + цена + первый media hash в пределах продавца |
| Подозрительная цена | отклонение от медианы категории > порога → мягкое предупреждение продавцу, не блокировка |
| Жалоба | `POST /reports` с причиной, объявление не скрывается автоматически |
| Блокировка | `POST /blocks` — блокирует диалог, не удаляет объявление |
| Спам | rate limit класса `publish` + лимит активных объявлений на пользователя |
| Свежесть (Bor/Yo'q) | подтверждение продлевает; без подтверждения — падение в ранжировании, затем архив |
| Срок объявления | по умолчанию 30 дней, продлевается |
| Verified seller | только через существующий onboarding + owner-подтверждение |
| Частник vs бизнес | видимый бейдж; бизнес получает `canOrder` |
| Несовершеннолетние | публикация требует Telegram-аккаунта; запрещённые категории отсекаются списком |
| Передача владения объявлением | **запрещена** — объявление принадлежит создавшему store навсегда |
| Модерация медиа | sniff по байтам уже есть; ручная очередь для жалоб |
| Запрещённые категории | явный список, проверка при публикации, отказ с объяснением |

**Запрещено категорически:** фейковые рейтинги, фейковые отзывы, фейковая срочность
(«осталось 2 штуки!»), накрутка просмотров.

# 34. SEO / public web implications

Текущее состояние: контент Mini App **структурно неиндексируем** — Telegram WebView плюс
`X-Robots-Tag: noindex, nofollow` на выдаче медиа.

Что нужно для роста из поиска (фаза 7):

- публичные страницы объявлений `/ru/bormi/e/{slug}-{id}/` и `/uz/...` с `Product` JSON-LD;
- публичные страницы продавцов `/ru/bormi/s/{slug}/`;
- страницы спроса «Ищу» — **только** если пройдёт privacy-review: обезличенный агрегат, никаких
  персональных запросов в индексе;
- генерация тем же prerender-конвейером, который уже делает 113 страниц и 124 статьи;
- IndexNow уже в проекте (`0007_indexnow.sql`);
- **блокер:** публичная страница требует публичного варианта отдачи изображений из R2. Текущая

- защита от thin content: объявление без описания и без фото не попадает в публичный индекс.

# 35. Accessibility plan

Базируется на pro-rules скилла и на том, что уже соблюдено в проекте (0 нарушений axe в 4 состояниях).

- цели ≥44 px; при переходе на 5 табов проверить 320 px и zoom 200 %;
- контраст ≥4.5:1 для текста в light и dark; сейчас `--muted: #666171` на `--paper: #ffffff`
  проходит, но новые вторичные подписи карточки (район, время) обязаны проверяться отдельно;
- один доминирующий action на экран — `ContactBar` не должен конкурировать с нижней навигацией;
- `role="alert"` для ошибок, `role="status"` для нейтральных обновлений — паттерн уже есть;
- каждая ошибка имеет названное действие восстановления;
- цвет не единственный носитель смысла: свежесть — цвет **и** текст;
- `prefers-reduced-motion` соблюдается;
- фокус видимый, порядок фокуса совпадает с визуальным;
- skip-link на главный контент — `#main-content` уже существует;
- известное ограничение: axe не вычисляет фон подписей нижней навигации из-за `backdrop-filter`.
  При переходе на 5 табов проверить контраст вручную.

## PHASE 0 — Reconciliation and evidence

### BM-0-01 · Восстановить видимость кабинета продавца — **PATH B РЕАЛИЗОВАН И ЗАДЕПЛОЕН 2026-08-03**

> **Владелец выбрал `AUTHORITY_PATH=B`.** Резолвер исправлен, задеплоен, покрыт
> 13 тестами. **Но он ничего не разблокировал**, и это не дефект реализации:
>
> ```text
> memberships                                     1
> memberships у Telegram-личностей                0   ← причина
> ```
>
> Единственный membership (`owner/active`) принадлежит личности с
> `provider = 'api'`. Она же значится владельцем в `telegram_agent_routes`.
> Ни одна из четырёх Telegram-личностей не имеет ни membership, ни onboarding.
> Path B выводит авторитет по `claims.sub`, а `claims.sub` в Mini App — всегда
> Telegram-личность. Совпадений нет ни у кого.
>
> **Остаётся owner-assisted binding plan** (гейт G-05b): связать Telegram-личность
> владельца с существующей организацией строкой в `memberships`
> (`role='owner'`, `status='active'`). Это запись в D1 и она **не выполнялась** —
> искусственные записи запрещены без отдельного решения владельца.
>
> После такой привязки Path B выдаст `sellerRead=true` без единой строки кода:
> это ровно то, что доказывает тест «an active owner membership over an active
> store is authority enough» (onboarding-строка в нём удалена).

**Реализованная модель:**

```text
SELLER_AUTHORIZED =
      (completed onboarding + active store)          ← прежний путь, не тронут
   OR (active owner membership + active store        ← новый путь
       + active organization)
  AND оба кандидата проходят один и тот же resolveSeller()
  AND MARKET_MINI_APP_SELLER_READS_ENABLED
```

`findOwnedActiveStoreByIdentity` принимает **только** identity: организация —
это ответ, а не вход, поэтому подставить чужой tenant нечем (в SQL ровно один
bind-параметр, тест это проверяет). Роль `staff` авторитета не даёт. Миграции не
потребовалось.

- **Фаза / приоритет:** 0 / P0
- **Проблема:** владелец не видит кабинет; причина доказана — 0 записей `sotuvchi_onboardings`.
- **Текущая возможность:** `resolveMarketAccess` требует completed-onboarding; альтернативы нет.
- **Предлагаемое поведение:** два пути на выбор владельца. **(A)** данные: создать запись onboarding
  + membership для Telegram-личности владельца. **(B)** код: добавить в `resolveMarketAccess`
  второй источник авторитета — активный owner-membership + активный store того же org.
- **UX-результат:** раздел «Магазин» появляется в кабинете.
- **Reuse:** 100 %.
- **API/домен:** путь A — ноль; путь B — изменение `access.ts`.
- **Файлы:** `functions/market/access.ts`, `functions/agents/sotuvchi/onboarding/*`.
- **Миграция:** нет. Путь A — запись данных (D1 write, требует разрешения).
- **Безопасность:** путь B расширяет поверхность авторитета — обязателен тест на изоляцию.
- **Аналитика / RU-UZ / доступность / производительность:** нет влияния.
- **Зависимости:** нет.
- **Тесты:** identity без membership не получает seller; identity с membership чужого org не получает.
- **Визуальные доказательства:** снимок кабинета с разделом «Магазин» на устройстве владельца.
- **Владелец:** **обязателен** — выбор пути и разрешение на запись в D1.
- **Трудоёмкость:** A — 0.5 д, B — 1 д. **Риск:** A низкий, B средний.

# 48. Exact recommended first implementation slice

**SLICE-1 = BM-2-01 «Кабинет-оболочка», строго без изменений API.**

Почему именно она безопаснее всего:

1. **Ноль изменений backend.** Ни одного нового эндпоинта, ни одного изменённого DTO, ни одной
   миграции. `rows_written` остаётся 0.
2. **Она чинит настоящую проблему обнаружения.** Seller tools перестают зависеть от переключателя
   в шапке, который владелец мог не увидеть.
3. **Она не трогает деньги и заказы.** Legacy-заказы переносятся как есть, checkout не задевается.
4. **Откат — один флаг.**
5. **Она — предпосылка всего остального:** «Ищу», сообщения, избранное, объявления живут в кабинете.

Границы слайса:
