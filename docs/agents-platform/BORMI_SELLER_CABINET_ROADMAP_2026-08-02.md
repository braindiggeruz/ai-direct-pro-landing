## 1. Что реально есть в коде (проверено чтением, не по отчётам)

### 1.1. Backend продавца — уже готов на ~70%

`functions/market/router.ts` отдаёт полноценную seller-поверхность.

**Чтение (GET):**

- `/seller/dashboard` — store + stats + 5 заказов + 5 вопросов одним ответом
- `/seller/stats`
- `/seller/orders`, `/seller/orders/{id}`
- `/seller/handoffs`, `/seller/handoffs/{id}`
- `/seller/products`, `/seller/products/{id}` (вместе с inventory)
- `/seller/categories`
- `/seller/inventory`

**Команды (POST/PUT/PATCH):**

- `/seller/orders/{id}/confirm|cancel|done`
- `/seller/handoffs/{id}/reply`
- `/seller/inventory/{productId}` (PUT, абсолютный остаток)
- `/seller/categories` (POST), `/seller/categories/{id}` (PATCH)
- `/seller/products` (POST), `/seller/products/{id}` (PATCH)
- `/seller/products/{id}/publish|unpublish|archive`

Все команды проходят через `requireSellerCommands`, требуют `Idempotency-Key`, rate limit `command`, и `expectedVersion` → `409 version_conflict`. Это уже правильная основа: exactly-once и защита от двойного тапа сделаны на сервере, кабинету не нужно их изобретать.

**Вывод:** новый кабинет — это не новый marketplace. Это новый фронт поверх существующих сервисов + 6–8 новых endpoint'ов.

### 1.2. Модель товара — сильнее, чем текущая форма

`functions/agents/sotuvchi/catalog/types.ts`:

```ts
CatalogProduct {
  categoryId, sku, name, description,
  priceMinor, currency: 'UZS',
  availability: 'available' | 'unavailable' | 'preorder',
  status: 'draft' | 'published' | 'archived',
  mediaRefs: string[],
  searchTerms: string[],                                   // ← мёртвый капитал
  specifications: { key, labelRu, labelUz, value }[],      // ← мёртвый капитал
  version
}
```

`searchTerms` и `specifications` добавлены миграцией `0027_market_catalog_quality.sql` и участвуют в ранжировании (`rankCatalogProducts`, `unmatchedConstraints` в голосовом и текстовом поиске). **Но в UI их нельзя заполнить вообще.** У всех товаров они пустые. Это прямая потеря релевантности поиска и будущего SEO.

### 1.3. Текущий кабинет — 19 KB, функциональный минимум

`apps/market-mini-app/src/screens/SellerApp.tsx`: 5 вкладок (dashboard / orders / questions / products / inventory).

Форма товара `ProductForm` — 5 полей: название, описание, цена, категория, наличие. И всё.

Конкретные болевые точки, найденные в коде:

1. **Фото добавить невозможно.** В форме нет ни одного элемента для медиа.
2. **`searchTerms` и `specifications` недоступны** — см. выше.
3. **Заказов видно максимум 5.** В роутере жёстко: `Math.min(5, boundedLimit(...))`. Не настройка UI — потолок API.
4. **Пагинации нет нигде** — `nextCursor` всегда `null`. Товары `limit=20`, вопросы `limit=20`.
5. **Дашборд — vanity, а не exception-first.** Три метрики (размещено / открытых вопросов / опубликовано) и два списка. «Что горит прямо сейчас» не видно.
6. **Настроек магазина нет вообще** — ни endpoint'а, ни экрана. Нельзя поставить паузу, часы работы, контакты, SLA.
7. **Статистика только за сутки.** `STATS_WINDOW_DAYS = 1`. 7д/30д backend физически не отдаёт.
8. **Цена вводится числом без маски** (`type="number"`, `priceMinor`), опечатка в разряде ничем не ловится.
9. **Конфликт версий показывается как голая строка ошибки** — без «перечитать и повторить».

### 1.4. Медиа — главный архитектурный барьер

`functions/platform/market/media.ts`: `mediaRefs` — это **Telegram `file_id`**. Отдача идёт через `proxyTelegramMedia` с заголовками:

```
Cache-Control: private, max-age=300
X-Robots-Tag: noindex, nofollow
Content-Security-Policy: default-src 'none'; sandbox
```

То есть:

- фото попадают в каталог **только через бота**, из Mini App загрузить нечего;
- картинки **принципиально неиндексируемы** — это правильно для приватного WebView, но делает SEO на этих URL невозможным;
- R2 в market-контуре не используется.

**Любой сценарий «сфоткал → товар» требует нового media-конвейера.** Это самый крупный кусок работы во всём roadmap.

### 1.5. AI-платформа — готова наполовину

`functions/platform/ai/`: фасад умеет `complete`, `structured` (с runtime-валидацией схемы), `transcribe`. Драйверы регистрируются по capability, есть policy/routes/fallback, таймауты, attempts, нормализация ошибок.

**Чего нет: vision.** `AiMessage.content` — это `string`. Картинку в модель отправить нечем. Нужен новый task `'vision'` + multimodal content в контракте + драйвер.

**Что уже работает и переиспользуется даром:** STT-цепочка Groq Whisper → OpenAI fallback, ключ Groq уже живёт в production, новых секретов для голосового ввода товара не нужно.

### 1.6. Публичного каталога для SEO не существует

`src/market/` — только `market.css`. `scripts/market-page.ts` рендерит **лендинги** (`/ru/sotuvchi/`, `/ru/market-doverie/`). Страниц товаров и магазинов в вебе нет.

При этом в проекте уже есть: prerender-конвейер, sitemap (240 URL), IndexNow (`0007_indexnow.sql`), blog/SEO-инфраструктура. То есть **рельсы для товарного SEO проложены, вагонов нет.**

## 2. Диагноз одной фразой

> Backend продавца почти взрослый, кабинет — детский, а самая дорогая работа продавца (завести товар) сейчас вообще невозможна внутри приложения.

Пока каждый товар заводится вручную пятью полями и без фото, продавец физически не может наполнить каталог. Всё остальное (заказы, вопросы, остатки) вторично: без товаров их просто не будет.

**Поэтому центр кабинета — не дашборд. Центр — конвейер добавления товара.**

## 3. Продуктовая идея: «Товар за 3 тапа»

Целевой сценарий, снятый по секундомеру:

```
тап 1   →  камера, 1–5 фото
   (2–4 сек AI)
тап 2   →  вписал цену (единственное обязательное поле человека)
тап 3   →  «Опубликовать»
```

Цель: **≤30 секунд на товар**, ≤3 обязательных касания. Всё остальное AI предлагает, продавец только подтверждает или правит.

Три режима ввода, один и тот же результат — черновик товара:

| Режим | Вход | Когда удобен |
|---|---|---|
| Камера | 1–5 фото | Основной. Товар в руках |
| Голос | «Наушники Sony, триста пятьдесят тысяч, пять штук» | Руки заняты, склад |
| Пачка | 10–40 фото подряд | Первичная заливка каталога |

### 3.1. Экран «Новый товар» после AI

```
┌──────────────────────────────┐
│ [фото] [фото] [+]            │
│                              │
│ Название                     │
│ Наушники Sony WH-1000XM4     │  ← AI, редактируемо
│ ○ Sony WH-1000XM4, беспро…   │  ← 2 альтернативы одним тапом
│ ○ Наушники Sony с шумопод…   │
│                              │
│ Цена, сум                    │
│ [_______________] ← курсор   │  ← ЕДИНСТВЕННОЕ поле продавца
│                              │
│ Остаток   [ 1 ] − +          │
│                              │
│ ▸ Описание (готово)          │  ← свёрнуто, AI заполнил
│ ▸ Характеристики: 6          │  ← свёрнуто
│ ▸ Поисковые слова: 14        │  ← свёрнуто
│ ▸ Категория: Аудио           │
│                              │
│ [   Опубликовать   ]         │
│  Сохранить черновик          │
└──────────────────────────────┘
```

Принципы:

- одно доминирующее действие на экран;
- AI-поля свёрнуты по умолчанию — продавец не читает то, что и так верно;
- у каждого AI-блока подпись «Составил Bormi» и один тап на правку (тот же паттерн, что уже принят в голосовом поиске: `Изменить` вместо обязательного подтверждения);
- цена и остаток — **всегда человек**, AI их не трогает (это прямой security-инвариант, а не UX-каприз).

## 4. AI-конвейер: фото → товар

### 4.1. Роль AI жёстко ограничена

Существующий инвариант из голосового поиска сохраняется дословно: **AI не владеет торговой истиной.**

AI **может**: прочитать изображение, предложить название, описание, характеристики, категорию, поисковые слова, alt-текст.

AI **не может**: назначить цену, назначить остаток, опубликовать товар, изменить статус, тронуть чужой магазин, придумать бренд/гарантию/доставку, которых нет.

Механика защиты: AI-эндпоинты **не пишут в каталог**. Они возвращают предложение. Запись идёт только через существующие `createProduct` / `updateProduct` с `Idempotency-Key` и `expectedVersion`. Публикация — только через `publishProduct`. Продавец — обязательная точка подписи.

### 4.2. Конвейер

```
фото (клиент, ≤10 MB, jpeg|png|webp)
  → сжатие в браузере до 1600 px          [клиент, экономит трафик и время]
  → POST /seller/media                     [новый]
      валидация magic bytes + размера
      R2: bormi-market-media/{orgId}/{storeId}/{uuid}.webp
      возврат: mediaId + подписанный handle
  → POST /seller/drafts/from-media         [новый, AI]
      vision-модель, structured output по схеме
      + грунтовка: категории и лексика ЭТОГО магазина
      → предложение (не запись)
  → продавец правит цену
  → POST /seller/products                  [существует]
  → POST /seller/products/{id}/publish     [существует]
```

Ключевая деталь качества: в prompt подаётся **словарь конкретного магазина** — существующие категории (`listCategories`) и `CatalogVocabularyEntry` (уже есть в контрактах каталога). Тогда AI предлагает «Аудио», которое у продавца уже есть, а не выдумывает новую категорию, и говорит языком его каталога.

### 4.3. Схема ответа AI (structured, валидируется на сервере)

```ts
interface ProductDraftSuggestion {
  names: [string, string, string];          // 3 варианта, ≤120 символов
  description: string;                      // ≤600, без обещаний доставки/гарантии
  categoryId: string | null;                // ТОЛЬКО из существующих категорий магазина
  categorySuggestion: string | null;        // если ничего не подошло — предложить новую
  specifications: { key, labelRu, labelUz, value }[];  // ≤8, только видимое на фото
  searchTerms: string[];                    // ≤20, ru + uz + латиница + опечатки
  altTextRu: string; altTextUz: string;     // для доступности и будущего SEO
  confidence: 'high' | 'medium' | 'low';
  uncertain: string[];                      // что модель НЕ смогла определить
}
```

`uncertain` — не техническая мелочь, а UX: поля, в которых модель не уверена, подсвечиваются продавцу как «проверь», остальное можно не читать. Честность вместо иллюзии всезнания.

### 4.4. Голосовой ввод товара — почти бесплатный

`POST /seller/drafts/from-voice` переиспользует уже задеплоенную STT-цепочку и уже написанный `parseBudget` (он умеет «триста пятьдесят тысяч» → 350000). Разница с покупательским голосом: результат идёт не в поиск, а в черновик.

Важно: распознанная цена **предзаполняется, но помечается как требующая подтверждения** — сумма голосом слишком дорого стоит при ошибке.

### 4.5. Пакетный режим

10–40 фото → очередь черновиков → продавец свайпает карточки, в каждой вбивает только цену → «Опубликовать все». Обработка фоновая, с прогрессом и возможностью уйти с экрана.

Для первичной заливки каталога это разница между «вечер работы» и «двадцать минут».

## 5. SEO: три уровня, и только один из них — про Google

Формулировка задачи владельца («чтобы приложение быстро по SEO поднималось») требует честного разделения. Контент Mini App **не индексируется**: это Telegram WebView, а медиа отдаётся с `X-Robots-Tag: noindex`. Никакая генерация текста внутри кабинета сама по себе не даст роста в Google. Рост даёт публикация того же контента наружу.

### Уровень 1 — внутренний поиск Bormi (эффект сразу, без деплоя веба)

`searchTerms` — это ровно тот механизм, который уже читает `rankCatalogProducts`. Генерация даёт:

- синонимы: «наушники / гарнитура / quloqchin / eshitgich»
- латиница и кириллица для узбекского
- частые опечатки и разговорные формы
- бренд в двух написаниях: «Sony / Сони»

Это напрямую поднимает recall голосового и текстового поиска — то, что уже живёт в продакшене.

`specifications` дают фильтрацию и честный `unmatchedConstraints` («цвет не совпал») вместо пустой выдачи.

### Уровень 2 — публичные страницы товаров (настоящее SEO)

Новый трек: генерация статических страниц из каталога тем же prerender-конвейером, что уже делает 113 страниц и 124 статьи.

```
/ru/bormi/t/{slug}-{id}/      товар
/uz/bormi/t/{slug}-{id}/
/ru/bormi/m/{store-slug}/     магазин
/ru/bormi/k/{category}/       категория
```

На каждой странице:

- `Product` JSON-LD: `name`, `description`, `image`, `sku`, `brand`, `offers` (`price`, `priceCurrency: UZS`, `availability`, `seller`)
- `BreadcrumbList`, `ItemList` на категориях, `Store` на магазине
- канонический URL, hreflang ru/uz, OG/Twitter
- CTA в Telegram с deep-link на конкретный товар: `t.me/BormiMarketBot?start=p_{id}`

**Обязательное условие:** публичные страницы требуют публичных изображений. Telegram-прокси для этого не годится (`private`, `noindex`, живёт по 5 минут). Поэтому R2 из раздела 4.2 — не только про загрузку, но и про публичную отдачу: `.../public/{hash}.webp`, immutable-кэш, три размера (480/800/1200), как уже делается для блога.

**Строгие правила публикации в веб:**

- в вебе только `status = 'published'` и только магазины, давшие явное согласие;
- цена и наличие на публичной странице обязаны быть свежими — иначе страница не рендерится (правило «stale цена противоречит обещанию Bormi» переносится сюда без изменений);
- страница с одним фото и пустым описанием **не публикуется** — это защита от thin content и от санкций за мусор в индексе;
- телефоны, адреса и любые контакты покупателей — никогда.

### Уровень 3 — скорость индексации

IndexNow уже в проекте (`0007_indexnow.sql`). Публикация товара → постановка URL в очередь IndexNow + добавление в sitemap. Новый товар попадает в индекс за часы, а не за недели. Это редкое преимущество, которое у Bormi уже оплачено прошлой работой.

### 5.1. Качество генерируемого текста — жёсткие рамки

- Узбекский пишется по конвенции проекта: **U+2018 в `o‘`/`g‘`**, U+2019 — только tutuq belgisi. Валидация на выходе AI, а не «потом поправим».
- Запрещены в описании: сроки доставки, гарантия, «оригинал 100%», «лучшая цена», любые обещания, которых магазин не давал. Это и SEO-риск, и юридический.
- Описание — про товар, а не про магазин. Без keyword stuffing: `searchTerms` существуют именно для того, чтобы не засорять текст.
- Каждое описание уникально; шаблонные абзацы «Купить X в Ташкенте» запрещены — Google их считает doorway-контентом.

## 6. Информационная архитектура кабинета

Пять вкладок остаются (мышечная память), но смысл первой меняется.

```
Сегодня        Заказы        Товары        Вопросы       Магазин
(exception)    (очередь)     (+ FAB)       (очередь)     (настройки+статы)
```

Остатки уезжают внутрь «Товаров» (это свойство товара, а не отдельная сущность в голове продавца) и дублируются быстрым действием на карточке заказа.

Плавающая кнопка **«+ Товар»** живёт на «Сегодня» и «Товарах». Проверить конфликт с bottom nav и compare tray в Telegram — в прошлом релизе FAB отклоняли именно по этой причине, здесь он нужен, значит нужен и отдельный QA-прогон на 320 px.

### 6.1. «Сегодня» — exception-first

Порядок блоков строго по срочности; **пустые блоки не рендерятся вообще**:

1. 🔴 Новые заказы (`placed`) — с возрастом: «17 мин»
2. 🟠 Заказы старше SLA
3. 🟠 Вопросы без ответа + TTL до истечения
4. 🟡 Опубликованные товары с нулевым остатком (продаются, но их нет)
5. 🟡 Черновики, которые продавец забыл опубликовать
6. 🟡 Товары без фото / без описания / без характеристик — «слабые карточки»
7. ⚪ Проблемы уведомлений (DLQ)
8. Только в самом низу — цифры за сутки

Если всё чисто — один экран: «Всё разобрано» и кнопка «Добавить товар». Пустое состояние — это не ошибка, это награда.

### 6.2. Заказы

- сегменты: Новые / В работе / Завершённые / Отменённые
- возраст крупно, поверх статуса
- карточка: товар, количество, сумма, возраст. Контакт покупателя — **только в детальном экране**, по явному открытию (PII-граница)
- действия свайпом: подтвердить / отменить
- на подтверждении сразу «остаток после: 4 → 3», чтобы решение было информированным
- конфликт версий (`409`) отрабатывается человеческим текстом: «Заказ изменился, обновили — посмотрите ещё раз», с уже перезагруженными данными и без потери намерения

### 6.3. Товары

- сегменты: Опубликованные / Черновики / Архив
- карточка: фото, название, цена, остаток, статус, значок «слабая карточка»
- быстрые действия: цена, остаток, снять с публикации — без входа в редактор
- поиск по названию
- бесконечная лента (нужен курсор на бэке)

### 6.4. Вопросы

Очередь без контента в списке (privacy) → детальный экран → ответ → уведомление покупателю ровно одно. TTL показывается таймером, истёкшие уезжают в архив.

### 6.5. Магазин

Настройки (новый бэкенд), статистика с честными окнами, поддержка, язык, пауза магазина.

**Пауза** — важная функция для реальной жизни: продавец уезжает, магазин перестаёт принимать заказы, витрина остаётся с честной пометкой. Сейчас единственная альтернатива — снять все товары с публикации, что разрушает SEO и историю.

### 7.2. Изменения существующих

- `/seller/orders` — снять потолок `Math.min(5, ...)`, добавить `status`, `cursor`; вернуть реальный `nextCursor`

- `/seller/dashboard` — переделать в exception-payload: не «последние 5», а «требующие внимания» с счётчиками

### 7.3. Миграции D1

Перед любой из них — обязательная сверка: в леджере `0025`, физически `0026–0030`. Слепой `wrangler d1 migrations apply --remote` запрещён (правило проекта, здесь оно повторяется, а не смягчается).

- `0031_market_media_assets` — R2-ключ, хеш, размеры, alt ru/uz, привязка к товару, кто загрузил
- `0032_market_ai_drafts` — что предложил AI, что принял продавец (для измерения качества; без PII, без сырого фото)
- `0033_market_public_catalog` — slug, признак согласия на публикацию, время последней публикации в веб
- `0034_market_store_settings` — часы, SLA, пауза, контакты магазина

### 7.4. Контракты платформы

- `AiTask` += `'vision'`
- `AiMessage.content` расширяется до `string | AiContentPart[]`, где part = `{type:'text'}` | `{type:'image', mediaType, data}`. **Обратная совместимость обязательна**: все существующие вызовы со `string` продолжают работать без правок
- `AiUnavailableError(..., 'vision')` — как уже сделано для `'transcribe'`
- R2-биндинг в конфиге Pages Functions

## 8. Feature flags

```

MARKET_SELLER_MEDIA_UPLOAD    загрузка фото
MARKET_SELLER_AI_DRAFTS       фото → черновик

## 9. Инварианты, которые нельзя нарушить

Переносятся без ослаблений: проверка `initData`; авторитет продавца выводится сервером; покупатель не может сам себя повысить; изоляция магазинов; публикация только серверной командой; idempotency; ровно одно движение остатка; ровно одно уведомление; TTL и владение handoff; никакого PII в аналитике; никакого прямого D1 с клиента.

Новое, специфичное для этого этапа:

- **сырое фото не логируется и не сохраняется дольше, чем нужно для обработки**; в R2 попадает только то, что продавец сознательно прикрепил к товару;
- **фото одного магазина недоступно другому** — ключ R2 включает `orgId/storeId`, отдача проверяет владение;
- **AI-предложение — не запись**; отдельный endpoint не имеет доступа к мутациям каталога;
- **предложение AI не может изменить цену, остаток или статус** — эти поля отсутствуют в схеме ответа физически, а не по договорённости;
- **публичная страница не показывает контакты покупателей** и не публикует магазин без явного согласия.

## 10. Тест-план

**Сервер:**

- media: неверный magic byte, превышение 10 MB, подмена content-type, чужой `storeId`, повторная загрузка того же файла
- drafts: AI вернул мусор → `AiStructuredOutputError`, не падение; AI предложил несуществующую `categoryId` → отбрасывается; AI попытался вернуть цену → поле игнорируется схемой
- пагинация: курсор не протекает между магазинами
- stats: окно 7/30 отдаёт ровно то, что посчитано, без экстраполяции
- store: пауза не отменяет уже размещённые заказы

**Mini App:**

- 320 px, 360 px, 430 px; light/dark; RU/UZ
- offline при загрузке фото — очередь и понятная ошибка, без потери черновика
- `409` в редакторе — данные перечитаны, введённое не потеряно
- камера запрещена → ручная форма остаётся
- targets ≥44 px, `role="alert"` на ошибках, реальные `<label>`, нет молчания интерфейса дольше ~300 мс (правила, уже принятые в голосовом релизе)

**Публичный веб:**

- валидность JSON-LD, канониклы, hreflang, отсутствие thin-страниц, отсутствие PII, корректный `noindex` для черновиков

**Существующие гейты без послаблений:** typecheck, ESLint, boundaries, secret scan, полный корпус тестов. Три унаследованных падения фиксируются поимённо и не маскируются.

## 11. Roadmap по фазам

Оценки — в человеко-днях одного разработчика, включая тесты.

### Фаза 0 — Сверка и канарейка (блокирующая) — 0.5 д

Git, deployments, Smart Placement, флаги, Telegram identity, D1 read-only, точный baseline тестов. Владельческая канарейка голоса и задержки запуска. Вердикт по v8-инциденту: `CLOSED` или `OPEN` с доказательством.

**Гейт владельца.** Пока не закрыто — кабинет не начинаем.

### Фаза 1 — Фундамент кабинета — 4 д ✅ СДЕЛАНО

Навигация, exception-first «Сегодня», реальная пагинация, снятие потолка в 5 заказов, свайп-действия, человеческая обработка `409`, состояния loading/empty/error/stale/paused, RU/UZ, тёмная тема, доступность.

Без AI и без фото. **Уже здесь кабинет становится пригодным для ежедневной работы.**

Риск: низкий. Откат: флаг `MARKET_SELLER_CABINET_V2`.

### Фаза 2 — Медиа-конвейер — 5 д

R2-биндинг, `POST /seller/media`, сжатие на клиенте, миграция `0031`, галерея в редакторе, перетаскивание порядка, обложка, alt-текст, публичный вариант отдачи (заготовка под фазу 5).

Риск: **высокий** — новая инфраструктура, новые расходы, новая поверхность атаки. Требует отдельного security-прохода.

### Фаза 3 — Редактор товара v2 — 3 д ✅ СДЕЛАНО

Характеристики, поисковые слова, маска цены с проверкой разряда, предпросмотр карточки глазами покупателя, публикация/снятие с явным подтверждением, черновик без потери данных.

Риск: низкий. Именно здесь оживает мёртвый капитал `searchTerms`/`specifications`.

### Фаза 4 — AI-студия — 6 д

`vision` в платформенном контракте, драйвер, `POST /seller/drafts/from-media`, грунтовка словарём магазина, экран «Новый товар» с AI-полями, `from-voice`, пакетный режим, миграция `0032`, метрика принятия предложений.

Риск: средний — качество модели на реальных фото из Ташкента непредсказуемо до пилота. Митигация: флаг, ручная форма всегда рядом, `uncertain` честно показывается.

**Гейт владельца** перед включением на реальном продавце.

### Фаза 5 — Публичный каталог и SEO — 5 д

Миграция `0033`, генерация страниц товаров/магазинов/категорий, Product JSON-LD, sitemap, IndexNow, hreflang, deep-link в бота, правила защиты от thin content.

Риск: средний — мусор в индексе лечится месяцами. Стартовать только на пилотном магазине с готовым каталогом.

**Гейт владельца:** публичный веб — это выход наружу, а не внутренняя фича.

### Фаза 6 — Магазин, статистика, онбординг — 4 д

Миграция `0034`, настройки, пауза, окна статистики 7/30 (сначала бэкенд, потом UI), онбординг продавца, чек-лист готовности к пилоту.

### Итого

**27.5 дня** до полного кабинета. Первая ощутимая ценность — на 5-й день (конец фазы 1). Возможность завести товар с фото — на 10-й (конец фазы 2).

**Фактически закрыто:** фазы 1 и 3 (7 дней по оценке) — без миграций, без новых секретов, без деплоя. Остаток: 20.5 дня, критический путь начинается с фазы 2.

```

параллельно:  Ф3 после Ф1 (не ждёт медиа)

## 12. Откат

- каждая фаза за флагом, выключение возвращает поведение мгновенно;
- D1 не откатывается никогда; все миграции — только additive, как `0027`;
- BFF откатывается на предыдущий deployment (текущий immediate rollback остаётся `e3aa4b9a-...` / `e4669b7`; полные ID подтверждать в Cloudflare, не по сокращениям);
- статический Mini App откатывается отдельно от бэкенда;
- публичные страницы снимаются переводом в `noindex` + удалением из sitemap, а не удалением URL (иначе 404 в индексе).

## 13. Метрики успеха

Измеряем поведение продавца, не тщеславие:

- **время на товар** (открыл форму → опубликовал): цель ≤30 сек с AI против сегодняшних минут;
- **доля принятых AI-предложений** без правки — качество модели, а не её наличие;
- **доля товаров с фото / с описанием / с характеристиками** — здоровье каталога;
- **время до ответа на заказ** и **на вопрос** — то, ради чего вообще нужен exception-first;
- **доля нулевых результатов поиска** до и после генерации `searchTerms` — прямая проверка гипотезы уровня 1;
- **страниц в индексе и переходов из поиска** — только после фазы 5.

## 14. Первый срез реализации

Когда владелец даст добро, первым пишется **не AI**, а самое дешёвое действие с самым большим эффектом:

1. снять потолок в 5 заказов и добавить курсор (сервер, ~0.5 д);
2. переделать `/seller/dashboard` в exception-payload (сервер, ~0.5 д);
3. новый экран «Сегодня» на этих данных (клиент, ~1 д);
4. свайп-действия по заказам с человеческим `409` (клиент, ~1 д).

Три дня, без миграций, без новых секретов, без деплоя веба, полностью за флагом. После этого продавец уже разбирает день в один экран — и на этой базе строится всё остальное.

## 15. Что осталось недоказанным

Честно, чтобы никто не принял план за факт:

- качество vision-модели на реальных фото узбекских продавцов **не проверено**;
- стоимость AI на объёме каталога **не посчитана** (нужен прогноз по пилоту);
- согласие реальных продавцов на публикацию их товаров в вебе **не получено**;
- выигрыш Smart Placement на валидном запуске **всё ещё не измерен** — это долг фазы 0, а не этого этапа;
- расхождение леджера миграций `0025` против физических `0026–0030` **не устранено** и блокирует любую новую миграцию.
