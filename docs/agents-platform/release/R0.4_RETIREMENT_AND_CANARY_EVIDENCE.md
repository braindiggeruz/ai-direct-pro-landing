## 2. Three real defects found, all pre-existing

These were not introduced by R0.4. They were found because the verification
looked at durable state rather than at response codes.

### 2.1 `LOGIN_ATTEMPTS` had no durable store — and hid it

The handoff recorded this binding as fixed and "verified behaviourally: five
failed logins accumulated across requests and produced HTTP 429". The binding
was in fact absent from the production Pages configuration.

The check passed anyway because `functions/lib/lockout.ts` falls back to an
in-isolate `Map` when the KV namespace is not bound, and five rapid requests
land in one isolate. The lockout therefore *looked* enforced while resetting on
every cold start and sharing nothing between isolates.

Root cause of the disappearance: **`wrangler pages deploy` replaces the Pages
project's binding and plain-text-variable configuration with whatever
`wrangler.toml` declares.** A binding that exists only in the dashboard is
deleted by the next direct upload. It had been set in the dashboard twice and
removed by a deploy twice — including once by the first deploy in this session,
which is how the mechanism was identified.

Fix: declare `LOGIN_ATTEMPTS` and `FIRST_PARTY_AUTOMATION_ENABLED` in
`wrangler.toml`, and record the rule in that file's header (D-027).

Verification changed from "did we get a 429" to "is there a durable key":

```
attempts 1-5 -> HTTP 401
attempt 6    -> HTTP 429  {"lockedFor":899}
KV key       -> login:<ip>:r04-lockout-probe@example.invalid, TTL 15 min
```

The probe used a throwaway identity, never the owner's admin email, and the key
was deleted afterwards.

### 2.2 The SEO schedule was live in production D1

`system_settings.seo_autopilot_schedule` held
`{"mode":"twice_weekly","active_days":[1,2,3,4,5,6,7]}`, written by
`system:e2e-test-session3` on 2026-06-21 — every day of the week, not twice.

The GitHub Actions scheduler was `disabled_manually`, so nothing was firing. But
the new Worker's Cron reads this same setting, so enabling first-party
automation would have started daily generation. Set to `disabled` before step 8.

### 2.3 `wrangler.automation.toml` could not deploy at all

`[limits] cpu_ms = 300000` is a paid-plan-only field; the account is on the
Workers Free plan and the API rejects the entire upload with error 100328. The
block was removed with a comment explaining why. The consumer is I/O-bound, so
the default CPU allowance is sufficient.

## 3. D1 inventory: 65 versus 67 resolved, zero loss

| Source | Count |
| --- | --- |
| Production `sqlite_master` tables | 67 |
| Post-migration export | 65 |
| Declared by migrations 0001-0024 | 64 |

```
67 = 64 application tables
   + d1_migrations   (migration-runner bookkeeping)
   + _cf_KV          (Cloudflare internal)
   + sqlite_sequence (SQLite internal, AUTOINCREMENT)
```

The export's 65 names match production **exactly** — zero names in either
direction. Indexes: 98 declared, 98 named present, 96 `sqlite_autoindex`, 194
total, zero missing. Rows preserved: `ai_drafts` 42, `seo_autopilot_jobs` 81.

Independently confirmed by rebuilding from scratch: a fresh database with
0001-0024 produces 64 tables and 98 indexes, and a staged upgrade (0001-0012,
then 0013-0024 — the path production actually took) produces a byte-identical
object set. `wrangler d1 migrations list --remote` reports no migrations to
apply.

Raw re-application of the SQL is deliberately **not** claimed to be idempotent:
migration 0003 uses `ALTER TABLE ... ADD COLUMN`. Idempotency belongs to the
runner, which records applied names in `d1_migrations`.

## 4. Sotuvchi production canary — 43/43

Run inside a temporary Worker bound to the production D1 database, so
`db.batch()` had production transaction semantics rather than a SQLite fixture's.
A secret-gated route, no `workers.dev` traffic beyond the run, deleted
immediately afterwards.

Invariants that matter most:

- **Order idempotency.** Three `confirmOrder` calls — two sharing one
  idempotency key, one fresh — produced one logical order row, `applied` then
  `unchanged` then `unchanged`.
- **Exactly one decrement.** Inventory 10 → 7 for a quantity-3 order, and
  exactly one `order_confirmed` movement. No negative inventory anywhere in the
  database.
- **Tenant isolation.** Tenant B could not resolve owner context for tenant A's
  org, read its product, mutate it, set its inventory, or read its handoff.
- **No fabrication.** A query sharing no token with the catalogue returned zero
  results; an unknown product id was refused with `CatalogNotFoundError` rather
  than answered. A real token still matched the real row, so the grounding is
  not simply "always empty".
- **PII.** No buyer name, phone, address or message text appeared in any
  analytics event. Contact data stayed in the order row's own contact columns.
- **Authorization.** Buyer denied seller transitions, seller reply and stats;
  anonymous denied stats.

Cleanup returned every table to its exact pre-canary count.

## 5. Automation canary — 56/56

Split into 13 phases because the Workers Free plan caps a request at 50
subrequests and every D1 statement is one. State carried across phases in the
production ledger, not in isolate memory. The deterministic checks used a
recording queue sender so they put no traffic on the live queue; two checks
deliberately used the real `AUTOMATION_QUEUE` and `AUTOMATION_DLQ` bindings to
prove the production wiring.

Notable results:

- A `retry_wait` job is **not** redeliverable before its backoff elapses — the
  first version of the canary mistook this for a defect, which is worth
  recording because the backoff is the behaviour, not a bug.
- The retry ceiling dead-letters instead of retrying forever: attempt 3 of 3
  moved the job to `dead_letter`.
- A non-retryable failure dead-letters at attempt 1 without consuming the
  ceiling.
- Replay is owner-only, tenant-scoped, and a second replay is a no-op that sends
  nothing and forks no row.
- `awaiting_review` is the only terminal success state. Nothing reached
  `completed`, so nothing could have been published.
- The real handler with no LLM provider key fails closed with
  `llm_provider_missing`, writes no draft, and moves no existing draft out of
  `pending_review`.

## 8. Remaining owner action

One, and it is optional rather than blocking: no LLM provider key is set on the
`gptbot-automation` Worker, so a Cron-scheduled `seo_draft_generation` job fails
closed with `llm_provider_missing` and writes nothing. Owner-triggered
generation through Pages is unaffected — Pages holds the provider secrets.
Cloudflare secrets cannot be read back, so the value has to come from the owner.

A second, cosmetic item is recorded in the owner kit
(`N8N_RETIREMENT_DEVIATION.md`): the kit's `workflow_disabled` evidence item
requires the n8n UI, which is not reachable. It does not affect GPTBot.
