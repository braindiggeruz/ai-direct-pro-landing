# Bormi Admin — продуктовая спецификация

Подзаголовок: Owner Control Center. Дата: 2026-08-03.

## 1. Зачем

Владелец открывает панель и за десять секунд понимает: работает ли всё, что
требует его вмешательства, сколько на площадке настоящих объявлений и продавцов,
где открытые заказы и вопросы, у кого есть доступ, какие флаги включены и что
происходило в системе.

Прежний Owner Control Center (`/admin-tools/agents/*`) это делает частично: он
вырос внутри SEO-админки, живёт в её оболочке и её роутере, и главный экран там
отвечает на вопросы платформы-агента, а не доски объявлений.

## 2. Аудит существующей админки

```
CURRENT_ADMIN_LOCATION=src/admin (внутри root-SPA), маршрут /admin-tools/*
CURRENT_ADMIN_BUILD=собирается вместе с маркетинговым сайтом (vite root)
CURRENT_ADMIN_ROUTES=SEO-раздел (14 экранов) + Owner Control Center (8 экранов)
CURRENT_ADMIN_AUTH=bearer в localStorage 'gptbot_admin_token', проверка api.me()
CURRENT_ADMIN_ROLES=platform_owner, support_readonly
CURRENT_ADMIN_API=/api/admin/* (owner-часть: /api/admin/agents/*)
CURRENT_ADMIN_DEPLOYMENT=Pages-проект ai-direct-pro-landing, ветка main
```

Ограничения, которые и стали причиной второй панели:

- один бандл с публичным сайтом: админка тянет его окружение и наоборот;
- IA от SEO-инструмента: «Cockpit», «Pages», «Blog», «IndexNow» рядом с магазинами;
- главный экран не отвечает на вопрос «что требует внимания»;
- нет качества карточек, нет состояния привязок, нет состояния системы;
- нет тёмной темы и адаптива под планшет;
- статусы показываются сырыми ключами.

Ничего из этого не является поводом удалять существующую админку: SEO-раздел
живой, Owner Control Center владеет всеми опасными командами и их
подтверждениями.

## 3. Архитектурное решение

**OPTION B** — новое изолированное приложение, переиспользующее auth и API.
OPTION C (замена) отклонён: существующая консоль остаётся fallback и владеет
командами.

```
BORMI_ADMIN_ARCHITECTURE=SELECTED (Option B)
путь        apps/bormi-admin/
сборка      своя (Vite 8, Tailwind 4, свой package.json и lockfile)
маршруты    свои (BrowserRouter basename=/admin)
бандл       независимый, каждый экран — отдельный chunk
auth        существующий owner-токен на том же origin
API         существующий /api/admin/* + один новый bounded endpoint
D1          недоступен из браузера
Mini App    не затронут ничем
```

Топология развёртывания: **/admin/ на существующем root-проекте** (вариант C
из рассмотренных). Причина — тот же origin, что и API: сессия владельца уже
существует на этом origin, поэтому не нужны ни CORS на admin-эндпоинтах, ни
второй способ передать токен. Отдельный домен `admin.bormi.uz` остаётся
возможным позже; он потребует отдельного owner-гейта и решения по DNS.

## 4. Информационная архитектура

В первом срезе показываются только разделы, за которыми стоит домен и данные:

```
ОБЗОР        Командный центр
ПРОДАВЦЫ     Магазины и доступы
БЕЗОПАСНОСТЬ Аудит
СИСТЕМА      Состояние
```

Спроектировано, но **не показывается**, пока нет домена или данных:

| раздел | чего ждёт |
|---|---|
| Объявления, Категории, Медиа | ADMIN-3: серверная пагинация и фильтры по каталогу |
| Модерация | самого домена модерации; черновик — не очередь модерации |
| Покупатели, Поиск и спрос | privacy-safe агрегатов поиска |
| «Ищу» / Bormi Match | домена wanted-request (не существует) |
| Заказы и вопросы | ADMIN-5: отдельные экраны поверх существующих endpoints |
| QuickPost | телеметрии QuickPost (события ещё не собираются) |
| Релизы, Инфраструктура, Миграции | частично есть в «Состоянии»; остальное — Cloudflare API |
| Жалобы, Инциденты | доменов нет |
| Настройки, Справочники, Правила | ADMIN-8 (записи) |

Пустой пункт меню не показывается вообще: меню, которое перечисляет девять
разделов и открывает четыре, перестаёт быть навигацией.

## 5. Экраны первого среза

**Командный центр.** Четыре KPI (опубликовано, черновики, активные магазины,
заказы в работе), блок «Требует внимания» (пункт с нулём не показывается),
качество карточек, свежие объявления, операции. Ни одного графика: рисовать
динамику не из чего, пока нет исторических событий, а декоративный график —
это ложь с осями.

**Магазины и доступы.** Состояние магазинов, права `sellerRead`/`sellerCommands`,
состояние церемонии привязки Telegram и счётчики кодов. Все опасные действия —
ссылками в существующий раздел, где у них есть подтверждение, причина и аудит.

**Аудит.** Последние события владельца, локализованные глаголы, без payload,
токенов и кодов. Только чтение — по устройству, а не по договорённости.

**Состояние.** Флаги (read-only), миграции, биндинги. Номер деплоя, версия
service worker и Smart Placement названы как недоступные изнутри Worker.

## 6. Дизайн

TailAdmin даёт каркас: сайдбар, хедер, карточки, таблицы, тёмная тема.
Bormi даёт смысл: фиолетовый как действие, лайм и коралл — редко и по делу,
остальное — нейтральные поверхности. Статус — это слово, цвет вторым сигналом.
Три радиуса, шкала отступов 4/8/12/16/24/32, системный шрифт (панель не ждёт
сеть, чтобы отрисовать число). Никаких emoji вместо иконок, никаких demo-фото.

## 7. Роадмап

| фаза | состояние |
|---|---|
| ADMIN-0 discovery | сделано (этот документ, инвентарь, матрица данных, безопасность) |
| ADMIN-1 shell и вход | сделано |
| ADMIN-2 командный центр | сделано в границах реальных данных |
| ADMIN-3 объявления и категории | следующая |
| ADMIN-4 продавцы и доступы (детали, действия) | после ADMIN-3 |
| ADMIN-5 заказы и вопросы | далее |
| ADMIN-6 QuickPost и поиск | только после появления телеметрии |
| ADMIN-7 безопасность и система (полностью) | далее |
| ADMIN-8 записывающие операции | отдельный security-review |
| ADMIN-9 production rollout | отдельный owner-гейт |
