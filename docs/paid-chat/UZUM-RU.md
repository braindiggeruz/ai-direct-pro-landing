# Оплата через Uzum Bank: как включить и обслуживать

*Пакет C, 2026-09-30; доводка WP-15, 2026-10-02. Источники: портал разработчика https://developer.uzumbank.uz/en/ и три публичные спецификации, скачанные 2026-09-30 в `docs/paid-chat/uzum-spec/`: Uzum Checkout 1.10.3 (`en_checkout.yaml`), Merchant API 1.0.0 (`en_merchant.yaml`), Fiscalization 0.0.2 (`en_fiscalization.yaml`). Ревью кода по спецификации — `docs/paid-chat/UZUM-REVIEW-2026-10.md`.*

## 1. Коротко

- Код готов и выключен. Пока не заданы `UZUM_API`, режим Uzum и секрет `UZUM_CREDENTIALS_JSON`, адреса Uzum отвечают 404, база не читается, кнопки Uzum в чате нет.
- Поддержаны оба продукта Uzum:
  - **Uzum Checkout** (`UZUM_API="checkout"`). Страница оплаты картой для сайта: принимает Humo и Uzcard любого банка. Посетитель нажимает «Uzum Bank», платит на странице Uzum и возвращается в чат.
  - **Merchant API** (`UZUM_API="merchant"`). Человек платит внутри приложения Uzum Bank: «To‘lovlar → gptbot.uz» и вводит **код аккаунта**. Код постоянный: 9 цифр, последняя — контрольная (алгоритм Луна), поэтому опечатку приложение отклоняет сразу. Сайт показывает код после того, как человек принял оферту. Сам экран с кодом делает WP-17 (окно «AI paket»); сервер уже отдаёт код (`/api/gpt/subscribe` и `/api/gpt/account`).
- Одновременно работает один из двух режимов.
- **Рекомендация для конверсии: Checkout.** Посетитель остаётся в привычном сценарии «нажал — ввёл карту — вернулся в чат», платить можно картой любого банка. В Merchant API человеку нужно открыть приложение Uzum, найти услугу и ввести код, и платить могут только клиенты Uzum Bank.
- Цена, пакет и доступ те же, что у Click: 20 000 сум, 300 ответов на календарный месяц от момента оплаты. Uzum пишет в тот же журнал, открывает тот же доступ и шлёт вам те же уведомления в Telegram.

## 2. Что спросить у менеджера Uzum

1. Какой продукт в договоре: Checkout (оплата картой на сайте), Merchant API (оплата в приложении Uzum Bank) или оба.
2. **Адреса API Checkout для теста и для боя.** В публичной спецификации их нет. Тестовый адрес по умолчанию `https://test-chk-api.uzumcheckout.uz` взят из стороннего SDK и **не проверен**. Боевого адреса по умолчанию нет, без него боевой Checkout не включится.
3. Для Checkout: `X-Terminal-Id` (UUID терминала) и `X-API-Key`, отдельно для теста и для боя.
4. Для Merchant API: `serviceId`, логин и пароль Basic-авторизации, отдельно для теста и для боя. В каталоге услуг Uzum: поле «код аккаунта» (9 цифр), сумма фиксированная 20 000 сум, название «AI paket 300».
5. Адреса уведомлений, которые нужно прописать:
   - Checkout (оплаты, возвраты и чеки): `https://gptbot.uz/api/payments/uzum`
   - Merchant API: `https://gptbot.uz/api/payments/uzum-merchant/check`, `…/create`, `…/confirm`, `…/reverse`, `…/status`. Уточните, дописывает ли Uzum `/check` и остальные к одному базовому адресу. Если да, базовый адрес `https://gptbot.uz/api/payments/uzum-merchant`.
6. **Подписаны ли уведомления Checkout и приходят ли они с фиксированных IP.** В спецификации подписи нет. Поэтому наш сервер никогда не верит уведомлению на слово: перед любым изменением оплаты он сам запрашивает статус заказа у Uzum своими ключами.
7. **Чеки.** Включена ли автофискализация на терминале Checkout. Если нет или если договор на Merchant API — нужен ключ Uzum Fiscalization API (тест и бой). Верны ли адреса из спецификации: тест `https://test-ofd.ipt-merch.com`, бой `https://ofd-key.inplat-tech.com`. Нужен ли `owner_type` (2 — услуга) и не нужен ли `commission_info` для собственной продажи (мы не комиссионер). Как пробивать чек оплаты рассрочкой или кэшбэком из приложения: тоже `card_amount` и тип 0 (продажа)?
8. Merchant API: повторяет ли Uzum `/create` с тем же `transId` после нашей ошибки и что делает после 10 неудачных `/status`.
9. Комиссия, сроки зачисления, частичные возвраты. Оферта с WP-24 обещает вернуть неиспользованную часть пакета (`OFFER-RU.md`): как сделать частичный возврат в кабинете и как Uzum пробивает его чек (корзина автофискализации и Fiscalization API).
10. Разрешено ли название «AI paket 300 · gptbot.uz». Слов «GPT» и «ChatGPT» в платёжных данных нет.
11. Актуальные тестовые карты: карты из спецификации истекают в сентябре и октябре 2026 года.

## 3. Чеки

Данные чека общие для Click и Uzum, решение владельца от 01.10.2026, значения уже в `wrangler.toml`:

- `GPT_FISCAL_IKPU = "10305008002000000"` — ИКПУ (SPIC) услуги по каталогу https://tasnif.soliq.uz/ (действует, маркировка не нужна).
- `GPT_FISCAL_PACKAGE_CODE = "1514296"` — код упаковки «услуга (раз)».
- `GPT_FISCAL_VAT_PERCENT = "12"` — ставка НДС. НДС **входит** в цену: в 20 000 сум 2 142,86 сум НДС.
- `GPT_FISCAL_TIN` — ИНН продавца (его передаёт только чек Click).

Кто печатает чек Uzum. Это решается в момент регистрации заказа и записывается в заказ (`gpt_uzum_orders.autofiscal`), поэтому смена настройки не делает двух чеков и не оставляет без чека уже начатую оплату:

- **Checkout с автофискализацией** (`UZUM_AUTOFISCAL="true"`): чек печатает Uzum. Корзина с ИКПУ уходит в регистрации и в возврате. Ссылка на чек приходит уведомлением, а если оно потерялось — сервер сам спрашивает `getReceipts` (при открытии панели и в кроне).
- **Checkout без автофискализации и Merchant API:** чек печатает наш сервер через Uzum Fiscalization API, той же очередью, что чеки Click (`gpt_fiscal_receipts`, `provider='uzum'`). Чек продажи — после оплаты, чек возврата — после возврата денег, если чек продажи был напечатан.

Поля чека Fiscalization API: товар «AI paket 300 (xizmat, 1 oy)», цена 2 000 000 тийинов, количество 1, ИКПУ, код упаковки, ставка НДС; вся сумма картой (`card_amount`); `date_time` — момент оплаты (возврата) по Ташкенту, как требует спецификация (в пределах суток); `payment_id` — номер платежа Uzum (`orderId` Checkout или `transId` приложения); `operation_id` — наш UUID, он сохраняется в базе **до** отправки и повторяется при каждом повторе, поэтому второй чек не появится. Телефон покупателя не передаётся (мы его не храним), поэтому кэшбэк по чеку Uzum не начисляется.

Боевая продажа не открывается без чека: `liveReadiness()` называет `UZUM_AUTOFISCAL`, если у Checkout нет ни автофискализации, ни ключа Fiscalization API, и `UZUM_CREDENTIALS_JSON.fiscal.live.apiKey` для Merchant API. Если хоть одно значение `GPT_FISCAL_*` пустое или неверное, новые оплаты Uzum не принимаются.

## 4. Как включить

### 4.1. Секрет `UZUM_CREDENTIALS_JSON`

Один секрет вместо шести: на бесплатном тарифе Workers число переменных ограничено. Задаётся в Cloudflare Pages → Settings → Environment variables, тип **Secret** (или `wrangler pages secret put` из файла). В файлы проекта, чаты и логи его не вставляйте.

```json
{
  "checkout": {
    "test": { "terminalId": "<UUID тестового терминала>", "apiKey": "<тестовый X-API-Key>" },
    "live": { "terminalId": "<UUID боевого терминала>", "apiKey": "<боевой X-API-Key>" }
  },
  "merchant": {
    "test": { "serviceId": 0, "login": "<логин>", "password": "<пароль>" },
    "live": { "serviceId": 0, "login": "<логин>", "password": "<пароль>" }
  },
  "fiscal": {
    "test": { "apiKey": "<тестовый ключ Fiscalization API>" },
    "live": { "apiKey": "<боевой ключ Fiscalization API>" }
  }
}
```

Разделы, которых нет в договоре, можно не заполнять. `serviceId` — число из договора, `0` в примере только место для него. Логин не может содержать двоеточие. Если JSON неверный, Uzum просто остаётся выключенным: сервер не угадывает и не подставляет значения.

### 4.2. Публичные настройки

Каждое значение пишем **в двух местах `wrangler.toml`**: в блоке `[vars.GPTBOT_RUNTIME_CONFIG]` и в упакованной строке `GPTBOT_RUNTIME_CONFIG_JSON`. Тест `tests/runtime-config.test.ts` не даст им разойтись. После правки нужен деплой.

| Ключ | Значение |
|---|---|
| `UZUM_API` | `""` — выключено; `"checkout"` или `"merchant"` |
| `UZUM_CHECKOUT_BASE_URL` | боевой адрес API Checkout от Uzum; только https и только домены uzumbank.uz, uzumcheckout.uz или uzum.uz |
| `UZUM_CHECKOUT_TEST_BASE_URL` | тестовый адрес; по умолчанию `https://test-chk-api.uzumcheckout.uz` (не проверен) |
| `UZUM_FISCAL_BASE_URL`, `UZUM_FISCAL_TEST_BASE_URL` | адреса Fiscalization API из спецификации: `https://ofd-key.inplat-tech.com` и `https://test-ofd.ipt-merch.com` (пустое значение — те же); только https и домены ipt-merch.com, inplat-tech.com или домены Uzum |
| `UZUM_AUTOFISCAL` | `"true"` только после того, как Uzum включил автофискализацию на терминале |
| `GPT_BILLING_MODE_UZUM` | `""` — как `GPT_BILLING_MODE`; `"test"`, `"live"` или `"off"` только для Uzum |
| `GPT_PAYMENT_PROVIDERS` | разрешённые провайдеры, по умолчанию `"click,uzum"` |
| `GPT_FISCAL_*` | см. раздел 3 |

Если Uzum выдаст адрес Checkout на другом домене, нужно поправить одну строку `UZUM_HOST_PATTERN` в `functions/lib/gpt-chat/uzum-config.ts` и `UZUM_CHECKOUT_HOST` в `src/gpt-chat/types.ts` (тест проверяет, что они совпадают); для Fiscalization API — `UZUM_FISCAL_HOST_PATTERN` там же. Эти списки защищают ключи: из-за опечатки в настройке ключ не уйдёт на чужой сервер.

### 4.3. Порядок запуска

1. **Миграции.** `0065_gpt_uzum_payments.sql` применена в R1. `0068_gpt_paid_chat.sql` (релиз R4) применяется **до** деплоя кода, как сказано в её шапке. Перед этим — резервная копия D1.
2. **Тест без денег (тёмный).** Посетители его не видят: Uzum в тесте предлагается только в сессии репетиции, то есть браузеру с cookie `__Host-gpt_rehearsal` от `POST /api/internal/gpt-rehearsal-session` (Bearer `GPT_BILLING_MAINTENANCE_SECRET`).
   - Checkout: `GPT_BILLING_MODE_UZUM="test"`, `UZUM_API="checkout"`, раздел `checkout.test`. Сайт регистрирует заказ на тестовом терминале и отправляет на тестовую страницу Uzum. Платите тестовой картой, уведомление открывает тестовый пакет. Протокол без сайта: `node --import tsx scripts/uzum-sandbox-rehearsal.ts` (с `--refund` ещё и возврат).
   - Merchant API: `UZUM_API="merchant"`, раздел `merchant.test`. Скрипт играет роль Uzum: `node --import tsx scripts/uzum-sandbox-rehearsal.ts --api merchant --simulate https://gptbot.uz` с `UZUM_CREDENTIALS_JSON` (раздел `merchant.test`) и `GPT_BILLING_MAINTENANCE_SECRET` в окружении. Он сам открывает сессию репетиции, получает код через `/api/gpt/subscribe` и проходит 22 шага: неверный пароль, опечатка в коде, код числом, неверная сумма, повтор `transId`, потерянный ответ `/confirm`, повторы, возврат, замена неподтверждённой оплаты новой. Без сайта то же самое: `--simulate local`.
   - Чеки: если в секрете есть `fiscal.test.apiKey`, тестовые чеки печатаются на тестовом хосте Fiscalization API. Ссылки на них Uzum просит прислать в их Telegram-чат для проверки, прежде чем выдать боевой ключ.
3. **Бой со скрытым запуском.** `GPT_BILLING_MODE_UZUM="live"`, `GPT_BILLING_LIVE_READY="true"` и всё, что называет `liveReadiness()` (тик обслуживания печатает этот список в `payments.uzum.missing`). Купите пакет сами: доступ открылся, в Telegram пришло «GPTBot.uz · AI paket: paid / uzum», в разделе «Мой пакет» есть ссылка на чек. Затем учебный возврат (раздел 7).
4. Откройте оплату всем.

## 5. Как это работает (для проверки)

**Checkout.**
- Посетитель вошёл, принял оферту и нажал «Uzum Bank». Сервер регистрирует заказ в Uzum: 2 000 000 тийинов, номер заказа `uzm_…`, возврат на `/uz/gpt-uzbek-tilida/` или `/ru/gpt-chat/` с `?pay=return`. Сессия оплаты 30 минут; повторное нажатие в это время открывает ту же страницу, второй заказ не создаётся.
- Уведомление Uzum (`/api/payments/uzum`) — только подсказка. Сервер находит заказ по двум номерам и сам запрашивает `getOrderStatus`. Доступ открывается, только если Uzum ответил `COMPLETED` и суммы и номера совпали. Неизвестный или чужой заказ — ответ 200 без единого запроса наружу. Если Uzum не ответил на запрос статуса — 502, и Uzum повторит уведомление (до 5 раз).
- Потерянное уведомление: заказ сверяется со статусом Uzum, когда посетитель открывает панель («Проверить статус», не чаще 6 раз в час на аккаунт), и в кроне через 35 минут после регистрации, даже если посетитель не вернулся. Просроченный заказ (12 часов) перед закрытием тоже сверяется: если Uzum говорит, что оплачено, — оплата засчитывается, а не теряется. Если Uzum недоступен, ничего не закрывается.
- Чек автофискализации без уведомления: сервер спрашивает `getReceipts` при открытии панели и в кроне в течение 48 часов после оплаты; через сутки без чека приходит `uzum_receipt_missing`.
- Крон берёт за тик до 5 заказов на каждый вид проверки. Заказ, который ответ Uzum не сдвинул (Uzum держит его `AUTHORIZED`, сумма не совпала и вам ушёл алерт, чека ещё нет) или который нечем спросить (нет ключей его режима, Uzum не ответил), ждёт: четверть своего возраста, от 15 минут до 6 часов (`uzumWait`, ожидание — строка `uzum_wait:<заказ>` в `gpt_billing_ops`, через сутки после конца ожидания удаляется). Поэтому пять «застрявших» заказов не занимают все места тика, и остальные сверяются вовремя (WP-24).

**Merchant API** (`/api/payments/uzum-merchant/<op>`).
- Логин и пароль Basic проверяются до чтения тела и до базы, схема в любом регистре, сравнение за постоянное время. Ответы — кодами Uzum (10001–10018, 99999).
- `/check`: код (числом или строкой, пробелы и дефисы допустимы) → аккаунт. Ответ `OK` с `account` и `product: "AI paket 300"`. Отказы: опечатка или чужой код — 10007; оферта изменилась, а владелец кода новую ещё не принял — 10007 (код снова работает, как только человек примет оферту на сайте); продажи остановлены (`GPT_BILLING_LIVE_READY="false"` и прочее из `liveReadiness()`) — 99999; у аккаунта идёт другая оплата — 10008.
- `/create`: заказ создаётся на лету, `request_id` = `transId`, сумма строго 2 000 000 (иначе 10011), повтор `transId` — 10010. Согласие с офертой переносится в заказ из кода (версия, ссылка, язык, время принятия).
- Одна оплата аккаунта за раз. Счёт другого провайдера, который тот ещё не видел, закрывается: человек платит через Uzum. Неподтверждённая прежняя оплата в приложении заменяется новой: её поздний `/confirm` получит 10015, и Uzum вернёт те деньги. Оплата, которую провайдер уже обрабатывает (страница Click, карта Checkout, подтверждаемая оплата в приложении), — 10008, пока не завершится.
- `/confirm` сначала записывает, что подтверждение пришло (`confirm_requested_at`), потом открывает пакет. Если посередине сбой (500), `/status` или повторный `/confirm` довершают оплату и отвечают `CONFIRMED`: Uzum уже списал деньги. Если не пришло ни то ни другое, крон через 10 минут довершает её сам и шлёт `uzum_confirm_recovered`: сверьте с кабинетом Uzum.
- Правило 30 минут: оплата без `/confirm` закрывается, `/status` отвечает `FAILED` 10015; крон закрывает такие оплаты сам.
- `/reverse`: до оплаты — отмена, после оплаты — возврат: пакет закрывается, а если чек продажи печатали мы — печатается чек возврата.
- Телефон из `/confirm` не записывается и не попадает в логи.

**Повторы безопасны.** Одно и то же уведомление или вебхук, пришедшие много раз, дают один доступ, одну запись в журнале, один чек и одно сообщение вам. Это проверяют тесты.

## 6. Алерты Uzum

Все `uzum_*` срочные и приходят в Telegram владельцу (`ALERTS-RU.md`):

- `uzum_amount_mismatch` — сумма или номер заказа в ответе Uzum не совпали, доступ не выдан;
- `uzum_partial_refund` — частичный возврат, доступ не тронут;
- `uzum_paid_after_cancel` — деньги списаны по заказу, который мы уже закрыли. Верните деньги или выдайте доступ вручную;
- `uzum_status_conflict` — после оплаты пришёл отказ;
- `uzum_processing` — ошибка сервера на уведомлении; Uzum повторит;
- `uzum_fiscal_failed` — чек через Fiscalization API не пробит после 6 попыток или за сутки после оплаты (повторы: 1, 5, 15, 60 минут, потом каждые 6 часов). Причина — `last_error` в `gpt_fiscal_receipts`: `config_missing` (ключ или `GPT_FISCAL_*`), `submit:uzum_1` (Uzum не принял ИКПУ или код упаковки), `submit:http_403` (ключ отклонён), `qr_pending` (Uzum принял чек, ссылки ещё нет), `sale_pending` (чек возврата ждёт чек продажи);
- `uzum_receipt_missing` — сутки после оплаты картой нет чека автофискализации; не чаще раза в сутки;
- `uzum_confirm_recovered` — оплату в приложении пришлось довершить после сбоя подтверждения.

Тестовые чеки алертов не шлют.

## 7. Возврат денег

Через наш сервер — только полный: так оферта возвращает пакет, из которого не использован ни один ответ. Неиспользованную часть (правило оферты, `OFFER-RU.md`, раздел «Возврат по правилу оферты») пока возвращают вручную в кабинете Uzum; отметить частичный возврат командой ниже нельзя (ответ 409, алерт `uzum_partial_refund`). Пока Uzum не подтвердит возврат, заказ остаётся оплаченным; пакет, по которому человек запросил возврат на сайте, уже заморожен.

**Checkout, вариант А: вернуть через наш сервер** (Uzum `POST /api/v1/acquiring/refund`):

```bash
curl -X POST https://gptbot.uz/api/internal/gpt-uzum-refund \
  -H "Authorization: Bearer <GPT_BILLING_MAINTENANCE_SECRET>" \
  -H "Content-Type: application/json" \
  -d '{"orderId":"uzm_…","confirmRefund":true}'
```

- Номер операции (`X-Operation-Id`) создаётся один раз и сохраняется до запроса в Uzum. Если связь оборвалась, повторите ту же команду: деньги не вернутся дважды.
- Ответ `requested: true` значит, что Uzum принял запрос. Заказ станет «возвращён», а доступ закроется, когда Uzum сообщит `REFUNDED`: уведомлением, сразу после запроса или при «Проверить статус».
- Корзина с ИКПУ идёт с возвратом ровно тогда, когда она шла с оплатой (заказ с автофискализацией), — что бы ни стояло в `UZUM_AUTOFISCAL` сейчас. Иначе Uzum вернёт ошибку 3045 или 3058. Чек возврата заказа без автофискализации печатает наш сервер.
- Возврат работает по ключам режима самого заказа, поэтому деньги можно вернуть и после того, как продажи Uzum выключены.

**Checkout, вариант Б: вернули в кабинете Uzum, отметить у нас:**

```bash
curl -X POST https://gptbot.uz/api/internal/gpt-uzum-refund \
  -H "Authorization: Bearer <GPT_BILLING_MAINTENANCE_SECRET>" \
  -H "Content-Type: application/json" \
  -d '{"orderId":"uzm_…","merchantRefundReference":"<номер возврата из кабинета>","confirmedRefund":true}'
```

Сервер сначала спрашивает Uzum. Отметка ставится, только если Uzum сообщает, что вся сумма возвращена. Иначе ответ 409, и ничего не меняется.

**Merchant API.** Вызова возврата в Merchant API нет: деньги возвращает Uzum и присылает `/reverse`, который закрывает пакет сам. Команда с `confirmRefund` для такого заказа отвечает 409 `uzum_merchant_refund`. Если Uzum вернул деньги без `/reverse`, отметьте это вариантом Б: статус спросить не у кого, поэтому записью служит ваше подтверждение, как у Click.

## 8. Выключение и откат

- **Остановить новые оплаты, не теряя подтверждений:** `GPT_BILLING_LIVE_READY="false"`. Новые оплаты не принимаются ни у кого (в приложении Uzum `/check` отвечает 99999), а уведомления по уже начатым продолжают приниматься.
- **Выключить Uzum полностью:** `GPT_BILLING_MODE_UZUM="off"`, `UZUM_API=""` или удалить секрет. После этого адреса Uzum отвечают 404, крон Uzum не работает. Делайте это, только когда открытые заказы Uzum закрылись: сессия Checkout 30 минут, оплата в приложении тоже 30 минут, счёт живёт 12 часов. Чеки уже оплаченных заказов печатаются и после выключения, пока в секрете есть ключ Fiscalization API.
- **Переключаться между Checkout и Merchant API** тоже стоит, когда открытых заказов Uzum нет. Открытый заказ Checkout держит оплату в приложении (10008), пока не завершится.
- Таблицы `gpt_uzum_orders` и `gpt_payment_codes` **не удалять**: это финансовые записи и коды, которые люди уже знают. Представление `gpt_payment_orders_all` можно удалить только вместе с откатом кода к версии до 0065.

## 9. Проверка в базе (только агрегаты)

```sql
-- заказы, которые крон сейчас ждёт (WP-24)
SELECT COUNT(*) FROM gpt_billing_ops WHERE org_id='gptbot-consumer' AND task GLOB 'uzum_wait:*';
```


```sql
-- заказы Uzum за сутки по режиму оплаты и состояниям
SELECT api, mode, state, COUNT(*) FROM gpt_uzum_orders
WHERE org_id='gptbot-consumer' AND created_at > (strftime('%s','now')-86400)*1000 GROUP BY 1,2,3;
-- чеки Uzum через Fiscalization API: напечатаны (0), ждут (-1), пропущены (-2)
SELECT kind, status_code, last_error, COUNT(*) FROM gpt_fiscal_receipts
WHERE org_id='gptbot-consumer' AND provider='uzum' GROUP BY 1,2,3;
-- оплаты в приложении, подтверждение которых не завершилось
SELECT COUNT(*) FROM gpt_uzum_orders WHERE org_id='gptbot-consumer' AND api='merchant' AND state='prepared' AND confirm_requested_at IS NOT NULL;
-- сколько аккаунтов получили код приложения
SELECT COUNT(*) FROM gpt_payment_codes WHERE org_id='gptbot-consumer';
-- сбои Uzum
SELECT code, COUNT(*) FROM gpt_service_alerts WHERE code LIKE 'uzum_%' GROUP BY 1;
```

## 10. Что не проверено

- Адреса API Checkout (тестовый взят из стороннего SDK, боевого нет) и формат ссылок тестового хоста Fiscalization API: тестовую ссылку не с `ofd.soliq.uz` сервер сохраняет, но панель её не покажет.
- Подпись уведомлений Checkout и IP-адреса Uzum: в спецификации их нет. Настройка `UZUM_WEBHOOK_IPS` не сделана: списка IP Uzum не давал, а защита держится на Basic (Merchant API) и на самостоятельном запросе статуса (Checkout).
- Формат ответа при повторном возврате с тем же `X-Operation-Id`. Код 3028 «операция уже существует» считаем принятым повтором.
- Присылает ли Uzum `DECLINED`, когда время сессии вышло. Если нет, такой заказ закрывает крон через 35 минут после регистрации.
- Как приложение Uzum передаёт код (числом, как в примере спецификации, или строкой) — принимаются оба.
- Что Uzum делает с оплатой в приложении после 10 неудачных `/status` (вопрос 8 раздела 2).
- Поля чека, которые спецификация не объясняет до конца: `owner_type`, чек рассрочки и кэшбэка (вопрос 7).
